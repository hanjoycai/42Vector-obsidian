🔌 外部可观测工具集成架构

AaaS 平台通过四大外部工具构建完整的数据采集管线，实现 Metrics · Tracing · Logging 三位一体的可观测能力

Op
Opik
LLM 可观测 & 评估平台 · by Comet ML · 开源
在 AaaS 中的角色：Agent 链路数据的主要采集器。通过 Python SDK（装饰器 + 上下文管理器）自动注入 Agent 框架（LangChain / Eino / CrewAI / 自定义），异步批量上报 Span 数据。支持 LiteLLM Callback 零代码接入（litellm.callbacks = ["opik"]）。
数据流向
⬅ Agent Runtime → Opik SDK 自动采集 Trace/Span（异步批量）
⬅ LiteLLM Callback → Opik（零代码采集所有代理流量）
➡ Opik REST API → AaaS 统一存储（Span Schema 标准化写入）
⟷ AaaS 注入 case_id/run_id → Opik Span metadata
核心采集：Trace/Span 树 · LLM Prompt I/O · Token 消耗 · TTFT · 工具入参/返回值 · 多模态附件
存储：ClickHouse（分析） + MySQL（事务） + Redis（队列） + S3（附件）
API：POST /v1/private/traces/batch · POST /v1/private/spans/batch · GET /v1/private/traces
Li
LiteLLM
统一 LLM API 代理网关 · 开源 · 100+ Provider
在 AaaS 中的角色：模型管理模块（5.1）的底层代理层。所有 Agent 的 LLM 调用均通过 LiteLLM Proxy（:4000）路由转发，支持 config.yaml 配置 Callback 链自动推送至 Opik/Langfuse/Prometheus。内置 30+ Prometheus 指标暴露于 /metrics 端点。
数据流向
⬅ Agent LLM Call → LiteLLM Proxy :4000 → MaaS API（路由/负载均衡/回退）
➡ Callback 推送 → Opik（Trace）+ Prometheus（Metrics）+ Slack（告警）
➡ /metrics 端点 → Prometheus Pull 采集 LLM 调用指标
⟷ AaaS 模型注册 → 自动同步 LiteLLM config.yaml 路由配置（M-09）
核心能力：API 统一 · 负载均衡 · Key 轮转 · 费用追踪 · 模型回退 · A/B 测试
关键指标：litellm_llm_api_time_to_first_token_metric · litellm_request_total_latency_metric · litellm_spend_metric · litellm_deployment_state
Callback 配置：success_callback: ["opik", "prometheus"] · failure_callback: ["slack"]
Pr
Prometheus
时序指标监控系统 · CNCF · Pull 模式
在 AaaS 中的角色：基础设施层硬件指标的核心采集器。通过三类 Exporter 定时 Pull 抓取指标：DCGM Exporter（:9400 GPU 硬件）、Node Exporter（:9100 系统）、vLLM /metrics（推理引擎），同时 Pull LiteLLM /metrics（LLM 调用指标）。
数据流向（全部 Pull 模式）
⬅ Pull :9400 DCGM Exporter → GPU 利用率/显存/温度/功耗/时钟/XID错误
⬅ Pull :9100 Node Exporter → CPU/内存/磁盘/网络吞吐
⬅ Pull vLLM /metrics → vllm:kv_cache_usage_percent · 队列深度 · 抢占数
⬅ Pull LiteLLM /metrics → LLM 调用量/延迟/Token/成本/部署状态
➡ PromQL API → AaaS 硬件监控 + 算力比对 + 告警规则
⚠️ 注意：KV Cache 指标来源于 vLLM Exporter（应用层），非 DCGM（硬件层）
查询 API：GET /api/v1/query（即时）· GET /api/v1/query_range（范围）· 默认 15s 抓取间隔
Lf
Langfuse
开源 LLM 工程平台 · 可自部署 · 备选集成
在 AaaS 中的角色：作为 Opik 的备选/补充方案。Langfuse 支持原生 OTLP/HTTP 协议接入（/api/public/otel/v1/traces），LiteLLM 可通过 callbacks: ["langfuse_otel"] 零代码切换。底层使用 ClickHouse + Postgres 存储，可完全自部署。
数据流向
⬅ Agent SDK / OTel Collector → Langfuse OTLP 端点（异步批量上报）
⬅ LiteLLM langfuse_otel Callback → 自动采集代理流量 Trace
➡ Langfuse REST API → AaaS 统一存储（Span 标准化适配）
⟷ 提示词管理：Langfuse Prompt Registry ↔ AaaS Prompt 双向同步
特色能力：开源自部署 · OTel 原生兼容 · Prompt Registry · 在线评估 · Session 分组
存储：ClickHouse（OLAP 分析） + Postgres（事务） + S3（原始事件） + Redis（队列）
数据模型：Trace → Observation（Generation / Span / Event） → Score

🔶 端到端验证测试 — 20 步详细执行流程

从「注册第一个模型」到「输出芯片商用报告」的完整操作路径，覆盖 AaaS 平台全部核心业务逻辑
Phase 1 · 配置准备
Step 1
注册推理模型
在模型管理模块注册 MaaS 平台已部署的模型：填写 API Endpoint、API Key、模型能力声明，执行连通性测试。注册完成后自动同步至 LiteLLM 路由表。
→ LiteLLM 代理层路由配置
Step 2
创建 Agent 应用
注册 Agent 应用实体：填写名称、场景类型（AI Coding / 长上下文 / 视频理解 / 视频生成），绑定推理模型，声明工具列表，标记芯片/集群环境标签。
→ Agent Runtime 配置
Step 3
创建提示词模板
在提示词管理模块创建 Prompt 模板：编写 System / User Prompt，插入变量占位符（{{input}} / {{output}}），发布版本。
→ 版本号锁定（v1.0）
Step 4
创建评测数据集
定义列结构（输入列 + 预期输出列），导入 Case 数据（CSV / JSON / 从 Trace 回流），支持多模态数据。发布版本后锁定为只读。
→ 评测集 v1.0 发布
→
Phase 2 · 实验设计
Step 5
配置评估器
创建评估器组合：
• 规则评估器 — 关键词/正则/JSON Schema 匹配
• LLM-Judge — 选择 Judge 模型 + 评分 Prompt + 量表配置
• 人工审核 — 配置维度和审核人
每个评估器通过快速测试验证后发布版本。
→ 评估器 v1 发布
Step 6
创建实验
四步配置向导：
① 基础信息 + 描述
② 选择评测集版本
③ 绑定评估器组（含权重）
④ 配置运行参数：模型参数预设、并发数、超时、芯片环境标签
实验 = 评测集v + Agent + 评估器 + 运行参数
Step 6b
克隆实验（可选）
基于已有实验快速创建变体实验：修改芯片环境、模型版本或参数预设，用于 A/B 对比验证（如 A800 vs NGU800P）。
→
Phase 3 · 运行执行
Step 7
发起实验运行
点击「运行」创建 Run 记录，引擎将实验元数据（experiment_id、run_id）注入 Span 上下文，按并发数分发 Case 到 Agent Runtime。
状态: 排队中 → 运行中
Step 8
Agent 执行 Case
每条 Case 触发 Agent 推理循环：
• 接收输入 → 🧠 思考规划（Planner）
• → 🛠 执行动作（Tool Call / LLM Call）
• → 👁 观察结果（Reflector）
• → 循环直至任务完成或超时

LLM 调用通过 LiteLLM 代理转发至 MaaS。
思考→行动→观察 多轮循环
Step 9
实时监控
运行时总览展示：进度条（已完成/总数）、QPS、TTFT、错误率、Token/s。失败 Case 实时列出，支持暂停/中止操作。
→ 5.5 运行时总览
→
Phase 4 · 数据采集
Step 10
Opik SDK 采集链路
Agent 框架 SDK 自动上报每个 Span：
• LLM 类型：Prompt I/O、模型参数、Token 数、TTFT
• Tool 类型：工具名、入参、返回值、延迟
• Agent 框架类型：节点类型、输入输出状态

AaaS 引擎注入的 case_id / run_id 随 Span 一同上报。
→ Span Schema (5.8.1) 标准化存储
Step 11
LiteLLM 记录调用指标
LiteLLM 代理层自动记录每次 LLM 调用的：
• 调用次数 · 错误率 · 延迟分布
• Token 用量（Input / Output / Cache Hit）
• 模型级费用追踪
→ AaaS 模型监控看板
Step 12
Prometheus 采集硬件
Prometheus 定期 Pull 抓取：
• GPU Exporter：利用率、显存、温度、功耗
• vLLM Exporter：KV Cache、队列深度
• Node Exporter：CPU、内存、网络
→ AaaS 硬件资源监控
→
Phase 5 · 分析评估
Step 13
自动评分
Case 执行完成后自动进入评分流程：
• 规则评估器同步执行
• LLM-Judge 异步调用 Judge 模型打分
• 人工审核分配给评审人
• 多评估器结果加权聚合为综合评分
每条 Case → 分项评分 + 综合评分
Step 14
实验结果分析
汇总看板：任务完成率、各维度评分均值、TTFT、延迟、Token 消耗。
Case 明细：逐条查看输入/输出/评分/Trace。
BadCase 标注：标记失败 Case + 填写归因标签。
Step 15
Trace 链路分析
从 Case 详情一键跳转 Trace 瀑布图/火焰图。分析每个 Span 的耗时分布（P50/P90/P99），定位性能瓶颈（🔥 标注慢 Span），排查错误传播路径。
Step 16
多实验 / 跨芯片比对
选择 2~4 个实验横向比对：
• 指标统计对比（差异自动标色）
• 逐 Case 输出 Diff
• 跨芯片模式：A800 vs NGU800P 全维度比对
• SLO 达标率自动判定
→
Phase 6 · 报告 & 闭环
Step 17
自动生成报告
实验完成后自动触发报告生成：
• 单实验验证报告（含效果/性能/成本图表）
• 比对报告（多实验差异分析）
• 芯片商用可行性报告（SLO矩阵+雷达图）
• 周期汇总报告
导出 PDF / Markdown / HTML
Step 18
算力比对看板
芯片性能雷达图（6维）· 指标对比矩阵（差异标色）· 延迟瀑布图（逐段芯片对比）· 吞吐量-功耗散点图 · 成本效率柱状图 · SLO 达标率面板 · 扩展性曲线
Step 19
BadCase 回流 🔄
将标记的 BadCase 一键回流至评测集，作为回归测试用例。从 Trace 数据中提取有价值的异常场景，自动生成 Case 草稿，人工补充预期输出后加入数据集。
→ 回流至 评测集(Step 4) · 闭环
Step 20
优化迭代
根据验证结果：
• 优化 Prompt → 新版本测试
• 调整模型参数预设 → 再次实验
• 反馈芯片瓶颈 → 硬件团队优化
• 克隆实验 → 下一轮验证
→ 回到 Phase 1/2 · 持续迭代

📐 数据流转标准（5.8）— 跨模块数据关联机制

Span/Trace Schema 标准（5.8.1）
trace_id 全局唯一 Trace ID（UUID v4）
span_id 当前 Span 唯一标识
parent_span_id 父 Span ID（根 Span 为 null）
span_name 操作名称（llm.chat / tool.search）
start_time / end_time ISO 8601 毫秒精度
status success / error / timeout
agent_id 关联 Agent 应用 ID
case_id / run_id / experiment_id 评测关联字段（注入）
model_name / input_tokens / output_tokens / ttft_ms LLM 扩展
tool_name / tool_input / tool_output / tool_latency_ms Tool 扩展
Trace ↔ 评测 双向关联机制
正向导航（Case → Trace）
Case 详情 → 点击「查看 Trace」→ 通过 case_id + run_id 自动匹配
面包屑：实验名 > Run ID > Case ID > Trace ID

反向关联（Trace → Case）
Trace 详情页顶部展示：关联实验名、Case ID、评测集版本
点击可跳转至 Case 详情（含评分和预期输出）

数据回流（Trace → 评测集）
选中 Trace → 「回流至评测集」→ 自动提取 Input/Output
生成 Case 草稿 → 补充 expected_output → 加入数据集
