- 小而专，而非大而全。
智能体应该像"专家团队"，各司其职。规划者只负责规划，总结者只负责总结，验证者只负责验证。这不仅降低运行成本，还使测试和修复更方便，结果更可预测。
- 强制结构化输出。
文本处理起来一团糟，JSON 才是王道。它易于调试、解析成本低，还能作为智能体之间的"契约"，支持自动验证，防患于未然。
- 解释"为什么"，不只"是什么"。
给智能体布置任务时，不要只说目标，更要解释任务的重要性，提供充分上下文。这能让智能体即使在简短提示下也能做出明智决策。
- 编排重于自主。
虽然"自主智能体"听起来很酷，但实际中你更需要"可预测性"。将所有已知逻辑（如条件判断、循环、重试机制、固定流程）从智能体提示词中抽出，交给编排层处理。
- 提示工程优先于微调。
模型出问题时，别急着微调。先问自己：是缺少事实（用 RAG 解决），还是格式不对或不符合品牌风格（再考虑微调）？Paweł 发现，80%的问题都源于提示词设计不佳。
- 工具描述要详细。
将工具描述视为微型提示词，指导智能体推理。说明何时、为何使用工具，应避免什么，最好附上几个示例。特别要说明工具如何组合使用。
- 缓存要到位。
智能体常对相同数据重复执行任务，如网站抓取。对这些重复响应进行缓存（如用智能体 ID 和输入内容的哈希值），能显著减少延迟和 API 成本。
- 共享协作产物。
如同人类协作时共享文档，让智能体通过共同编辑文档、计划或代码来协作。通常，下一个智能体甚至不需要获取产物的全部内容。
- 记录一切。
没有日志，就没有学习。记录所有输入、输出、重试、工具调用和智能体思考过程。添加应用维度（如客户类型、用例），然后分析错误，设计评估器。
- RAG 的问题可能不在检索。
许多人专注于高级检索策略（分块、重排、HyDE），但 Paweł 发现 RAG 真正的痛点往往是"数据整理"——这项无人愿做的苦活。在生产环境中，90%的情况需要混合 RAG，结合语义搜索（向量搜索）和元数据过滤。
- 限制智能体可访问的工具。
将智能体连接到众多工具看似强大，却会塞入过多上下文，增加推理难度，更不提安全风险。明智之举是限制工具访问。
- 创建限定范围的 API 密钥。
为每个外部系统定义角色（如 Stripe 订阅分析师、Sigma 报告员），为各角色创建专用 API 密钥并分配给智能体。这能有效控制权限。
- 建立提示词库。
别让提示词散落在工作流中。将它们存入版本控制仓库（如 Git），或至少放在 Google 表格中，按名称和版本访问。这才是工程师的思维方式。
- 大型智能体工作流构建状态机。
对于长期、复杂的业务流程，应设计成状态机，明确定义状态（如发票的"已提交"、"待审批"、"已支付"）和状态转换。这样即使出问题，也能恢复到之前状态，方便重新运行。
