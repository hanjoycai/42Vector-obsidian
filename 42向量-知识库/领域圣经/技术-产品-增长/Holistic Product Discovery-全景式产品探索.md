# 本文旨在揭示产品发现过程的奥秘

## 一、有效的产品具备的特征

- **商业层面**：能够盈利。
- **用户层面**：让用户感到满意。
- **技术层面**：具有可行性，能够被构建。

## 二、避免单方面视角

- 不要仅仅专注于自己的部分，忽略整体的平衡。

## 三、为什么很难构建能够达成目标的技术？

### 3.1 常见的心理偏见

- **确认偏误**：低估与己方观点不符的事实，却高估支持己方信念的信息。
- **乐观偏误**：我们通常认为自己遭遇负面事件的可能性比他人低。
- **输出价值低估**：想法本身无用，除非它能解决实际问题。
- **宜家效应**：如果我们自己是创作者，我们倾向于高估自己创建的东西的价值。
- **未经挑战的假设**：由于确认偏误，假设往往未被质疑。低估假设错误的后果很容易。
- **沉没成本谬误**：当人们感觉已经投入了过多的时间和精力时，他们不愿接受浪费，进而坚持错误的方向。
- **孤岛式工作**：每个人都专注于执行，而非挑战现有假设。
- **输出过多谬误**：认为工作量越多，结果就会越好。

## 四、产品构建的复杂性

### 4.1 功能使用率

- 仅有 **20%** 的已构建功能会被用户频繁使用。
- **30%** 的功能极少或几乎从未被使用（**50%**）。

### 4.2 创业失败的原因

- **42%** 的初创企业失败是因为市场需求不足。

## 五、产品开发中的经验教训

- 不要总是听取客户的意见。
- 承认测试结果。
- 不要在时间压力下工作。
- 过多的资本会增加复杂性。

## 六、软件项目的两个关键阶段

| 阶段 | 目的 | 价值类型 |
| --- | --- | --- |
| **发现阶段** | 确定要构建什么；确保创造的内容有价值。 | 知识 |
| **交付阶段** | 实现构建；将创意付诸实践。 | 价值 |

## 七、发现阶段的重要性

- 数据来源：[nngroup.com](http://nngroup.com/)
- **有发现阶段**：
    - 成功率：**83%**
    - 中立结果：**13%**
    - 失败率：**4%**
- **无发现阶段**：
    - 成功率：**52%**
    - 中立结果：**32%**
    - 失败率：**16%**

## 八、关键要点与最佳实践

### 8.1 构建错误与正确所需的努力相同

- **约翰·奥尔斯帕（John Allspaw）**：构建错误产品与构建正确产品所需努力相当。

### 8.2 高管的关注点

- 高管更关注交付而非发现，因为交付的进展更容易衡量。

### 8.3 发现阶段的核心

- 最大化影响：通过确定要构建的内容实现。
- 减少浪费：通过明确不该构建的内容实现。

### 8.4 实用准则

- **经验法则**：发现阶段应占总开发时间的约 **10%**。

## 产品发现原则

## 一、问题优先于解决方案

- **爱上问题而非解决方案**：
    - 聚焦于问题本身，而不是急于找到解决方案。
- **深入挖掘问题的核心**：
    - 彻底理解问题的本质，确保解决方案切中要害。
- **时刻牢记问题**：
    - 不要忘记你正在解决的问题，始终将其置于首位。

## 二、结果优先于输出

- **关键在于结果和影响**：
    - 真正重要的是产品达成的成果和对用户及市场的影响，而非单纯的产出数量。

## 三、团队多样性、信任与开放优于个人努力

- **倡导多样性与包容性**：
    - 包括多样性、包容性、心理安全感以及团队协作。
- **多样化团队的优势**：
    - 多样化团队在创新方面表现优于单一团队，创新能力提升 **20%**，风险降低 **30%**。
    - 数据来源：Deloitte 多样性与包容性革命报告。

## 四、全局视角优于局部优化

- **汲取多学科的宝贵见解**：
    - 从不同领域中获取独特的视角，避免局限于单一学科。
- **跳出孤岛思维**：
    - 超越自己的职责范围，聚焦于公司整体需要达成的目标。

## 五、持续发现优于无计划的探索

- **感知并响应未来**：
    - 在复杂领域中，未来永远无法预测。唯一有效的方式是通过感知变化并迅速作出响应。

# 发现框架

## 一、有效发现的原则

- **任何方法都需要良好的反馈循环**：
    - **迭代性**：通过重复流程收集反馈，为下一次改进提供依据。
    - **增量性**：以小批量工作方式进行，每次递增都基于前一次的成果。
- **成功产品的三个特质**：

| 特质 | 问题 |
| --- | --- |
| **可行性** | 我们应该构建这个产品吗？ |
|   | - 是否帮助实现业务目标？ |
|   | - 是否满足业务需求？ |
|   | - 是否属于业务战略的一部分？ |
| **可取性** | 他们需要这个产品吗？ |
|   | - 是否帮助客户获得正确结果？ |
|   | - 是否以高效方式满足客户需求？ |
|   | - 是否满足客户的需求？ |
| **可实施性** | 我们能够可持续地构建这个产品吗？ |
|   | - 是否符合现有产品和服务生态系统？ |
|   | - 是否适合当前业务？ |
|   | - 是否具备必要的能力和资源？ |
|   | - 是否合理且符合长期构建计划？ |
|   | - 如何构建？采用什么技术？ |

## 二、如何满足客户需求，同时可持续地构建产品并建立可持续业务？

- **三种主要风险**：
    - 用户价值风险
    - 业务价值风险
    - 可行性风险
- **应对风险的方式**：
    - 在项目开始时明确风险。
    - **最低限度的发现**：确定需要做的最少发现工作，以应对特定风险。
- **推荐书籍（了解伦理风险）**：
    - 《数字同情》（Digital Compassion），作者：Peter Axborn
    - 《未来伦理》（Future Ethics），作者：Cennydd Bowles
    - 《设计师的行为准则》（A Designer’s Code of Ethics），作者：Mike Monteiro

## 三、双钻模型（英国设计委员会提出）

![[Notion/42向量/领域圣经/成长-关系-职场/assets/《10x Is Easier Than 2x》10倍比2倍容易/image 301.png]]

### 3.1 用户中心设计（UX）框架

- **发散阶段**：更广泛或更深入地探索问题。
- **聚焦阶段**：集中行动，解决问题。

### 3.2 双钻的两个主要阶段

1. **钻石1：探索问题空间**
    - 与客户交流，获取见解，明确问题。
2. **钻石2：探索解决方案空间**
    - 生成潜在解决方案，并通过原型验证这些方案。
- **循环迭代**：这不是一个线性过程，可能需要多次循环。

### 3.3 四个明确阶段

| **钻石1：找到正确的问题** | **步骤** |
| --- | --- |
| 1. 探索问题 | - 发现问题。 |
|   | - 谁是利益相关者？ |
|   | - 谁是用户？ |
|   | - 环境和背景是什么？ |
| 2. 结构化问题 | - 整理见解并创建简洁的解释。 |
|   | - 对问题区域进行分类。 |
|   | - 得出结论并验证问题定义。 |
|   | - 确定解决方案发现的范围。 |

| **钻石2：找到正确的解决方案** | **步骤** |
| --- | --- |
| 3. 创新解决方案 | - 提出可能的解决办法。 |
|   | - 产生广泛的创意集合。 |
| 4. 验证解决方案 | - 确保解决方案能够真正解决问题。 |
|   | - 创建快速可测试的原型。 |
|   | - 以明确最终要构建的内容为结束。 |

# 4. 强大的整体框架

## 一、双钻模型中的四阶段与价值结合

| **阶段** | **钻石1：探索问题** | **钻石2：解决方案创新** |
| --- | --- | --- |
| **业务价值** | 探索问题：市场格局如何？ | 结构化问题：市场的缺口在哪里？ |
|   | 创新解决方案：如何利用市场机会？ | 验证解决方案：解决方案是否实现预期成果？ |
| **用户价值** | 用户上下文是什么？ | 最重要的用户需求是什么？ |
|   | 哪些解决方案可以满足需求？ | 哪些解决方案最能满足需求？ |
| **可行性** | 我们当前的能力是什么？ | 我们的主要实际机会是什么？ |
|   | 我们能构建什么？ | 我们应该如何可持续地构建？ |

## 二、框架的功能与应用

- **系统化考虑三大风险**：在双钻框架的每个阶段，系统化地评估 **业务价值**、**用户价值** 和 **可行性**。
- **表格化可视化工具**：通过表格工具突出场景或实际技术，帮助明确每个阶段的重点。

## 三、框架的实际用途

- **帮助理解历史和现状**：
    - 该框架可以帮助你了解过去或当前采取的发现方法。
- **评估方法的全面性**：
    - 是否良好地评估了风险？
    - 是否全面理解了问题的范围？
    - 是否选择了最聪明的方式来可视化解决方案？
    - 评估是否使用了适合的方式来验证解决方案是否符合需求？
    - 这些活动是否能够带来最大的学习？

## 五、三角测量的力量

- **通过发现阶段使用多种方法**：
    - 每个部分使用多种方法，确保覆盖尽可能多的范围。

# 5. 产品发现操作手册

## 一、操作手册的作用

- 操作手册帮助团队在发现过程中导航：
    - **已知与未知的操作手册**：
        - 问题复杂性各异。
        - 有些问题易于解决，而有些问题需要大量研究。
        - 越难的问题需要更多的努力，才能找到根本原因。

## 二、已知操作手册：聚焦于用户价值

3. **假设**：
    - 假设：我们相信客户有 [问题X]。如果我们提供 [解决方案Y]，我们将看到 [预期结果Z]。
    - **提示**：不要拘泥于结构，明确要解决的问题、解决方案的概述以及预期结果。
4. **设计工作室**：
    - 用演示文稿阐明问题，与团队一起绘制解决方案。
    - **展示**：向团队展示解决方案。
    - **反馈**：批评和质疑关键问题，确保解决方案能真正解决问题。
    - **迭代**：多次循环，直到团队对问题和解决方案达成共识。
5. **原型**：
    - 创建可测试的实际原型。
6. **用户测试**：
    - 在真实用户身上测试原型。
    - **推荐阅读**：*Rocket Surgery Made Easy*
7. **团队展示**：
    - 向更大的利益相关者群体和同事展示，获取业务和组织的反馈。

## 三、未知操作手册：聚焦于用户价值

8. **研究问题**：
    - 与团队一起举办研讨会，收集有关主题的研究问题。
    - 创建便签的亲和图，将问题分类。
    - **点选投票**：确定最重要的研究问题。
9. **用户研究**：
    - 使用三种来源收集研究数据（如分析、用户访谈、客户支持）。
    - **验证数据**：从多个角度进行数据验证。
10. **设计冲刺**：
    - 综合见解并创造实际的解决方案。
    - **优势**：专注、时间限制、功能性，邀请来自不同视角的人参与。
11. **团队展示**：
    - 邀请更广泛的群体审查已完成的成果并提供反馈。

## 四、将产品与设计功能结合

- **避免孤立的设计职能**：
    - 避免设计团队单独在工作室模式下工作，与其他职能脱节。
    - 这样可能导致发现结果与业务优先级无关，最终半途而废，缺乏清晰的学习成果。
- **实现透明化**：
    - 展示每个项目的进展情况。

| **已知** | 假设<br>- 项目 A<br>- 项目 B | **设计工作室** | 原型设计<br>- 项目 C<br>- 项目 D | 用户测试<br>- 项目 E | **团队间距** |
| --- | --- | --- | --- | --- | --- |
| **未知** | **研究问题** | 用户研究<br>- 项目 F | **设计冲刺** | 用户测试<br><br>- 项目 G<br>- 项目 H | **团队间距** |

- **这样做的好处**：
    - 更多的发现将转化为交付。
    - 产品与设计之间的关系将得到改善。
    - 产品的发现能力将变得更强。
    - 发现时间与业务目标相匹配。
    - 提升透明度，了解重点。
    - 增强团队的通用词汇和工具包。

# 6. 战略性产品发现

## 一、设定并衡量目标

- **早期设定可衡量的目标**：
    - 为业务价值和客户价值设定可衡量的目标。
    - 尽可能经常跟进这些目标。
- **将目标表达为期望的结果**：
    - 强调目标达成后将实现的影响或变化。
- **在整个过程中保持目标的清晰连接**：
    - **工具**：
        - **机会树**（Opportunity Trees，作者：Teresa Torres）。
        - **影响映射**（Impact Mapping，作者：Gojko Adzic）。
    - **结构化问题空间探索**：
        - 在开发过程中优先排序问题。
- **SMART目标的设定**：
    - 目标需具体（Specific）、可衡量（Measurable）、可达成（Attainable）、相关性强（Relevant）、有时限（Time-based）。
- **结果导向目标**：
    - 目标应以结果为导向，以便与具体解决方案无关。
- **影响映射的应用**：
    - 当重点分布在不同类型用户群体中时，影响映射是一种有效的工具。

| **结果** | **通过 X 达成更多的 Y 或 Z** |
| --- | --- |
| **目标群体** | 群组 A |
|   | 群组 B |
|   | 群组 C |
| **需求** | 需求 X |
|   | 需求 Ya |
|   | 需求 Yb |
| **行动** | 行动 Ta |
|   | 行动 Tb |

## 二、持续衡量业务价值和用户价值的成果

- **保持战略性思维**：
    - 在产品开发的整个过程中，从起点到最终交付，始终关注业务价值和用户价值的成果。

| **阶段** | **活动** |
| --- | --- |
| 探索问题 | - 找出结果 |
|   | - 找出需求 |
| 结构化问题 | - 设定目标 |
|   | - 基线测量 |
| 创新解决方案 | - 估算目标达成的范围 |
| 验证解决方案 | - 测量需求 |
| 构建解决方案 |   |
| 衡量成果 | - 衡量结果 |
|   | - 衡量需求 |

## 三、可行性发现的核心问题

- 公司内部有哪些现成的技能？
- 当前使用的技术是否可能过时？
- 有哪些新技术可以采用？
- 我们应如何可持续地构建事物？
- 我们需要开发哪些新能力？
- 我们需要如何重组以满足未来的需求？

## 四、工具与方法

- **使用 Wardley 映射**：
    - 将用户需求映射为能力。
- **利用 Thoughtworks 技术雷达**：
    - 找到潜在的新解决方案，并通过构建尖刺（spike）来验证其可行性。

# 7. 发现与交付的关系

## 产品发现与交付的协同

- **产品发现**：弄清要构建什么。
- **产品执行**：负责构建产品，包括：
    - **产品定义**。
    - **产品交付**。
- **避免混淆产品定义与发现**：
    - 产品发现并不总是告诉我们应该构建某些东西。
    - 重点在于找到需要解决的正确问题，并为该问题找到正确的解决方案。
- **发现与交付的关系**：
    - 发现 → 学习 → 知识。
    - 交付 → 创造成果 → 价值。

## 发现与交付的切换难点

- 在发现与交付之间切换并不容易，因为它们关注不同的内容且有着不同的特性。
- 发现并不是一个阶段，而是一种需要持续的心态。
- **反馈与学习**：
    - 如果反馈表明对问题的理解不够充分，说明需要进行更多的发现。
    - 保持信心，继续发现。

## 实践建议

- **寻找虚拟墙**：
    - 在发现与交付之间寻找虚拟墙，通过协作和反馈循环取代隔离。
- **Sprint Zero（冲刺零阶段）**：
    - 不要误解，它是为构建做准备，而不是发现。
- **设计冲刺**：
    - 打破孤岛，帮助团队集体关注于发现。
- **整体性产品发现**：
    - 使用结构化的方式进行发现。
    - **双轨Scrum**：确保发现与交付相辅相成，而不是彼此干扰。

## 节奏与信号

- **节奏**：节奏是发现与交付切换过程中的关键，它提供了反馈循环。
- **信号**：信号指示何时需要采取新行动，例如通过连续的定量和定性测试来评估学习成果。
    - **关键问题**：
        - 我们是否已经掌握了足够的知识？
        - 风险是否足够低？

## 赋能团队与三人组角色

- **角色分工**：
    - **设计师**：关注用户视角和用户价值。
    - **产品经理**：关注业务视角，确保产品价值。
    - **工程师**：关注技术视角，负责可行性。
    - **团队协作**：根据需要引入额外的专业知识。

## Spotify发现简表

- **灵感来源**：Spotify的发现模型 "Data, Insight, Belief, Bet"。
    - **数据**：我们看到了哪些趋势？（客户、销售、技术）。
    - **洞察**：基于数据，我们能利用哪些明确的见解？
    - **假设**：基于洞察，我们假设了什么？
    - **成功**：成功的表现是什么样？

## 发现故事与看板

- **发现故事**：
    - 将发现与交付结合，通过发现故事推动优先事项。
- **发现看板**：
    - 专注于最高优先事项，平衡学习率与开发率。

## Cynefin复杂性模型（作者：Dave Snowden）

- **复杂问题**：
    - **促进性约束**：松散耦合，“探测 → 感知 → 响应”。
    - **实践**：通过逐渐显现的实践解决问题。
- **复杂化问题**：
    - **治理性约束**：紧密耦合，“感知 → 分析 → 响应”。
    - **实践**：通过最佳实践解决问题。
- **混乱问题**：
    - 缺乏约束，“行动 → 感知 → 响应”。
    - **实践**：通过新颖实践解决问题。
- **清晰问题**：
    - 紧密约束，“感知 → 分类 → 响应”。
    - **实践**：通过最佳实践解决问题。

## 风险分级与应对策略

- **风险等级划分**：
    - **无风险**：显而易见的问题，直接交付。
    - **低风险**：复杂化问题，通过发现操作手册降低风险。
    - **中风险**：复杂问题，使用整体性发现框架迭代解决。
    - **高风险**：可能影响产品失败的复杂问题，通过快速验证假设降低风险。

## 关键问题与迭代

- **关键问题**：
    - 我们对问题理解得有多透彻？
    - 我们对解决方案理解得有多深入？
    - 我们是否清楚解决方案以有效、可持续的方式解决了问题？

## 精益创业与发现交付结合

- **精益创业循环**：
    - **构建 → 测量 → 学习**：类似于科学方法和实验。
- **结合循环**：
    - **发现驱动循环**：基于发现的构建、测量、学习。
    - **交付驱动循环**：基于交付的构建、测量、学习。
- **从已交付的成果中学习**：反馈推动新的发现。

## 持续协作的发现与交付

- **无风险问题**：
    - 直接交付：**构建 → 测量 → 学习**。
- **低/中风险问题**：
    - 第一步：使用发现操作手册（例如三角测量法、双钻模型）。
    - 第二步：交付（构建 → 测量 → 学习）。
- **高风险问题**：
    - 第一步：发现假设并快速验证。
    - 第二步：交付（构建 → 测量 → 学习）。

# 8. 如何开始

## 理解文化的重要性

- **无法进行良好发现的四大主要原因**：
    1. 缺乏时间和预算。
    2. 缺乏支持，难以证明价值。
    3. 没有涉及合适的人。
    4. 无法接触用户。
- **现有流程可能会阻碍良好的发现过程**。

## 三种类型的变革

12. **操作型变革**：
    - 改善现有的工作内容。
13. **过渡型变革**：
    - 改变现有的流程。
14. **转型型变革**：
    - 改变心态和行为，包括组织和文化变革。

## 了解你的变革模型

### 1. **ADKAR 模型**（Jeff Hiatt 提出）

- 专注于变革的五个关键要素：意识（Awareness）、愿望（Desire）、知识（Knowledge）、能力（Ability）、强化（Reinforcement）。

### 2. **八步变革模型**（John Kotter 提出）

- 逐步指导如何实现成功的变革。

### 3. **变革模型**（Kurt Lewin 提出）

- **解冻阶段（Thawing）**：
    - 为变革做好准备。
    - 确立变革的必要性。
    - 准备离开舒适区。
    - 传递令人信服的信息，帮助人们放下过去。
    - 对问题的本质有深入的洞察。
- **过渡阶段（Transitioning）**：
    - 实施所需的变革。
    - 这是一个过程或过渡期。
    - 在变革过程中让相关人员参与：
        - 获取反馈。
        - 确定变革是否有效。
    - 达成共同理解。
- **冻结阶段（Freezing）**：
    - 使变革成为永久性的。
    - 开发可持续的方式来支持变革。
