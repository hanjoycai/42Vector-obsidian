# 为什么我们写这本书

- **关于产品运营存在许多困惑**：
    - 产品运营通过大规模优化系统，帮助团队和领导层更清晰地了解产品表现，从而促进更好的战略决策。
- **产品运营是释放产品管理价值的关键**：
    - 将洞察整合到业务、客户和流程中，具有极高的价值。
- **产品运营的定义**：
    - 产品运营是帮助产品管理功能实现大规模化的学科。它提供支持，确保团队获得必要的输入以制定战略、确定优先级，并优化工作方式。
- **产品运营的三大支柱**：
    1. 数据与洞察。
    2. 客户与市场洞察。
    3. 流程与管理。

---

# 第一部分：产品运营简介

---

## **产品管理的挑战**

- **多重职责**：
    - 产品经理需要同时关注产品执行、战略和流程管理。
    - 如果产品战略讨论准备困难，可能影响执行时间。
    - **数据对产品经理的重要性**：
        - 即使是经过培训的产品经理，没有数据也难以胜任工作。

---

## 1. **为什么需要产品运营**

- **多产品组合的复杂性**：
    - 不同团队和跨职能协作中，信息分散、流程各异，难以共享。
- **产品运营的作用**：
    - 帮助产品经理专注于产品战略，并赋能组织做出更好的决策。
- **专注于最需要的支柱**：
    - 找出组织中最大的痛点与机会。

---

## 2. **什么是产品运营**

- **产品运营的本质**：
    - 产品运营帮助产品管理功能实现规模化，提供所有必要输入以支持战略制定和优先级排序。
- **产品战略的来源**：
    - 通过实验逐步制定目标。
    - 没有核心数据支持的战略，往往是无依据且代价高昂的。
- **跨职能协作**：
    - 产品运营将组织整合，帮助确定实现目标的方式。
- **减少挫折感**：
    - 让决策更简单透明，而不是直接替代决策。

---

## 3. **产品运营的三大支柱**

1. **业务数据与洞察**：
    - 收集并分析内部数据，支持战略制定和监控。
    - 提供产品指标，帮助高层做出战略决策。
2. **客户与市场洞察**：
    - 聚合并简化外部研究，提供团队所需的市场工具。
3. **流程与实践**：
    - 通过一致的跨职能合作，扩展产品管理价值。
    - 定义产品操作模型，包括战略制定、协作方式等。

# 第二部分：支柱 1 - 业务与数据洞察

### **实现数据与洞察能力的步骤**

4. **理解需要回答哪些问题**：
    - 这些问题将帮助您制定产品战略。
5. **确定需要跟踪哪些数据**：
    - 以回答这些关键问题。

7. **创建基础仪表盘**：

## **4.从产品视角解读数据**

- **产品运营中的关键要素**：
    - 收入与成本分析是产品运营流程的重要组成部分。
- **需要的证据**：
    - 每月产品盈利能力。
    - 用户或公司使用情况。
    - 新产品和现有产品的状态。
    - 市场数据（包括竞争者和客户关键绩效指标）。
- **产品运营的整合作用**：
    - 将数据整合到一个可视化工具中，实时访问并用于分析。

---

**跟踪的典型数据类型**

| **类别** | **数据类型** |
| --- | --- |
| **产生收入的产品** | 总收入、年度经常性收入（ARR）、合同价值 |
| **所有相关产品的参与度** | NPS、功能采用率、新推广评分 |
| **研发支出** | 总研发费用、间接产品成本 |
| **内部工具的活动成本** | 内部成本、吞吐量指标成本 |

- **经验丰富的产品经理可以通过数据讲述产品战略的故事**。

## **5. 提出正确的战略问题**

---

## **战略层次**

| 战略要素 | 内容 | 时间范围 |
| --- | --- | --- |
| 公司愿景 | 产品组合和产品凝聚力的北斗星。关注如何为客户提供差异化价值。<br>- 5-10 年后我们想成为什么样的人<br>- 对客户的价值、市场地位、企业面貌 | 首席执行官和 SLT |
| 战略意图 | 确定并围绕成果进行调整，以确定战略并证明组织各级职能部门的执行力<br>- 阻碍我们实现愿景的商业挑战<br>- 不超过三个（帮助引导您 | SLT |
| 产品组合战略举措 | 确定实现产品和职能业务成果所需的关键举措的优先次序。<br>从产品组合的角度来看，我们可以解决哪些问题来实现战略意图？ | 首席采购干事和副总裁 |
| 产品战略与举措 | 我们可以解决哪些问题，以实现产品组合的愿景，并应对每个产品所面临的业务挑战。 | 副总裁和总监 |
| 选项 | 每季度优先考虑特定团队在冲刺周期内要开展的工作，以交付计划。<br>- 我可以制定不同的解决方案来解决这些问题，以实现我们的目标 | 产品团队 |

---

### **明确战略意图的问题**

- **了解业务现状和趋势**：
    - 通过不同维度（客户群、地域等）切片分析数据。
- **制定产品举措的问题**：
    - 产品收入是否与支出匹配？
    - 不同客户群是否购买了不同的产品包？
    - 现有产品的使用率是否足够？

---

### **明确选项的问题**

- **团队需要划分产品指标**：
    - 理解不同客户类型和群体的趋势。
- **产品运营的支持**：
    - 确保团队拥有必要的数据和工具，实时监控结果并调整决策。


## 6. 数据可视化

- **步骤**：
    1. 确定需要回答的问题。
    2. 构想最终状态。
    3. 找到数据存储位置。
    4. 补充缺失的监测工具。
    5. 手动创建仪表盘。
    6. 实现自动化。

---

### **产品指标审查**

- 关键问题：
    - 参与度数据是否已启用？
    - 使用了哪些工具？
    - 事件标签何时实施？
    - 我们能测量所有产品/功能的参与度吗？
    - 数据捕获的理想状态是什么？

---

### **核心参与度指标**

- **产品粘性**：
    - 日活跃用户数 (DAU)、周活跃用户数 (WAU)、月活跃用户数 (MAU)。
- **使用频率**：
    - 用户登录次数。
- **功能采用率与留存率**。
- **产品使用数据**：
    - 深度：按时间、漏斗等衡量。
    - 广度：活跃用户数量。

---

### **资源分配数据**

- **用途**：
    - 了解资源分布和分配。
- **分桶方法**：
    1. 战略性工作（如产品创新）。
    2. 技术债务与平台改进。
    3. 日常运营 (BAU)。
    4. 缺陷修复。

# 第三部分：支柱 2 - 客户与市场洞察

---

## **研究的真正价值**

- **研究的输出必须可供产品团队使用，否则毫无意义**。
- **民主化研究**：
    - 提高学习速度。

---

## **第七章：研究支柱**

- **产品经理需要与客户对话**：
    - 许多管理者担心客户会因反馈和测试请求而感到厌烦。
- **产品运营的帮助**：
    - 设置系统，帮助产品经理获取关键战略决策所需的洞察。
- **洞察来源**：
    - 销售中的赢/输分析。
    - 网站上的客户评论。
    - 支持电话和电子邮件。
    - 其他团队的生成性和评估性用户研究。
- **聚焦研究中的最大空白**：
    - 行业趋势、市场规模、竞争分析。

---

## **第八章：客户洞察**

- **客户洞察的目标**：
    1. 利用现有数据。
    2. 轻松开展生成性和评估性研究。
    3. 使研究结果可访问并可被所有团队使用。
- **关键问题**：
    - 如果公司通过销售和支持进行大量客户对话，必须找到让产品团队利用这些洞察的方法。
- **实现客户研究功能**：
    1. 创建数据目录。
    2. 为数据分类，明确其来源和意图。
    3. 创建 360° 数据视图。

---

## **第九章：简化用户研究**

- **缩小信息差距**：
    - 用户访谈可以填补空白。
- **常见问题**：
    - 产品经理可能避免与客户对话。
    - 销售周期可能阻碍用户访谈。
- **重点**：
    - **使研究活动、工具和系统更易于组织访问**：
        1. 创建用户数据库：
            - 记录所有研究。
        2. 创建用户研究存储库：
            - 保存以往研究的笔记、视频和发现结果。
- **研究角色与责任**：
    - 用户研究员主导方法论。
    - 产品经理参与研究，理解洞察。
    - 产品运营支持工具和系统的实施。

---

## **第十章：市场研究**

- **市场研究的作用**：
    - 评估潜在市场的价值。
    - 量化不同市场中的潜在机会。
    - 帮助衡量产品战略的权衡取舍。
- **评估扩展机会的价值**：
    - 考虑市场规模和竞争格局。
    - 合同比较：竞争者的合同周期是什么样的？
- **关键术语**：

| **术语** | **缩写** | **定义** |
| --- | --- | --- |
| **总可服务市场** | TAM | 如果能捕获整个市场的潜在价值。 |
| **可服务市场** | SAM | 基于当前产品或未来产品，在地理区域内可捕获的 TAM 部分。 |
| **可获取市场** | SOM | 考虑开发时间、竞争和销售能力后，实际可捕获的 SAM 部分。 |

- **计算这些术语**：
    1. 耗时且需要市场知识。
    2. 模型通常提供范围（最优与最差场景）。
    3. 或需要分析师的支持。

# 第四部分：支柱 3 - 创建产品运营模型、流程与实践

---

## **产品管理流程**

- **标准化程度**：
    - 在大型公司中，销售、工程和客户成功团队通常遵循明确的流程。
    - 产品运营将创建更严格的产品管理流程。
- **跨职能协作的重要性**：
    - 产品团队往往在规划阶段未能充分吸引跨职能利益相关者。

---

## **第十一章：产品运营模型**

- **重新定义“流程”**：
    - 将其转变为“方法”或“服务”，例如为产品经理提供实用支持。
- **API 型产品运营**：
    - 产品运营应像 API 产品一样，迭代方法并提供服务。如果这些方法无用，应予以淘汰。
- **核心理念**：
    - 产品运营的目的是提高决策质量和速度，而非完全依赖流程。
- **产品运营模型的作用**：
    - 转化业务和产品战略为可执行的工作。
    - **指导内容**：
        - 路线图规划。
        - 战略审查。
        - 年度计划。

---

## **第十二章：创建产品运营模型的流程与治理**

| **内容** | **示例** |
| --- | --- |
| **角色与职责** | 职位描述、职业发展路径。 |
| **产品团队流程** | 模板、发现、路线图、工具栈、SDLC。 |
| **跨团队合作指南** | 创意管理、SDLC、发布指南与 GTM。 |
| **治理与年度计划** | 会议节奏、跨职能协作接触点。 |

- **活动示例**：
    - 标准化产品角色与职业阶梯。
    - 设定模板和工具，促进跨职能协作（例如路线图）。
    - 实现自动化报告节奏，监控指标与成果。

---

## **第十三章：治理与产品规划**

- **关键问题**：
    1. 工作是否与产品战略保持一致？
    2. 是否定期审查 OKRs 或 KPIs？
    3. 是否有合适的人员实时决策？
- **优秀治理的特点**：
    - 包括产品监督、风险管理、合规性和持续改进。
    - **数据与洞察**：
        - 是监控与对齐的核心。
- **治理节奏**：
    1. 战略讨论的节奏。
    2. 跨职能协作接触点。
    3. 将正确的洞察传递给正确的人，促进更好的决策。

---

## **治理会议示例**

| 节奏 | 示例 | 谁 | 重点领域 |
| --- | --- | --- | --- |
| 年度 | 公司启动仪式 | 整个组织 | - 产品组合/产品战略和路线图 |
| 季刊 | 季度业务回顾 | 执行团队和跨职能领导 | - 审查 OKRs、计划进展情况并预测重大问题<br>- 注重成果和业务目标，而不是产品设计或细节 |
| 季刊 | 跨职能路线图审查 | 工程、销售、市场营销、客户服务、法律 | - 审查进度、风险、相互依存性或优先举措<br>- 收集高层次的反馈意见<br>- 合作开展下一步工作 |
| 每月 | 路线图审查 | 主要的跨职能领导 | - 审查路线图和战略性产品方向，提出问题<br>- 不在范围内：错误、资源配置 |
| 每月 | 演示日 | 销售、营销、CS | - 解释阶段（阿尔法与贝塔）以及何时可以出售<br>- 向人们介绍新功能和增强功能 |
| 双周 | 敏捷产品-团队流程 | 工程、Scrum 领导 | - 审查冲刺状态、风险和依赖性<br>- 地址拦截器、监视器 |

## **会议描述**

- **公司启动会议**：
    - 产品团队陈述战略和主题。
- **季度业务审查 (QBR)**：
    - 评估产品指标对战略目标的对齐程度。
    - 聚焦结果和业务目标。
- **路线图审查**：
    - 审查产品路线图的依赖关系和进展。
- **演示日**：
    - 展示产品的改进与新特性。
- **敏捷流程**：
    - 审查冲刺状态，解决依赖与阻碍。

## **产品运营的治理作用**

- **优先级框架**：
    - 使用加权评分和延迟成本分析方法。
    - 创建模板和议程以支持会议和讨论。
- **目标**：
    - 建立“非此即彼”的权衡文化，而非“全要”的氛围。
    - 提供透明的产品开发进展。

# 第十四章：为产品经理定义流程

---

### **流程审计与标准化**

- **当前问题**：
    - 路线图格式零散且通常不依赖数据。
- **目标**：
    - 审核流程和模板，确保产品能力的有效性。

---

### **“适度足够”的流程**

- **治理的意义**：
    - 确保团队专注于高 ROI 活动。
- **流程设计**：
    - 提供工具和技能支持团队工作。
    - 帮助新产品经理上手并培养强大的团队。

---

### **需要标准化的核心领域**

- **领域**：
    - 想法管理。
    - 路线图规划。
    - 产品工具包。
    - 团队入职。

---

### **想法管理**

- **系统的作用**：
    - 跟踪想法来源，避免失去背景。
- **产品运营的帮助**：
    - 建立流程，将正确的信息传递给相关人员，并反馈想法的状态。
- **关键问题**：
    - 跨职能伙伴和客户应如何提交请求或想法？
    - 如何确保提交格式有用？
    - 如何反馈想法的进展或状态？
- **建议**：
    - 使用专用工具（如 ProdPad）。
    - 保持提交者知情：如果不采纳请求，解释原因并提供判定标准。

---

### **路线图规划**

- **常见争论**：
    - 使用什么格式？谁可以访问？规划的范围应有多远？
- **产品运营的贡献**：
    - 简化路线图展示方式并使其更具结构化。
- **路线图的目的**：
    - 是一种沟通工具，应根据受众需求量身定制。
- **针对不同受众的路线图**：
    - **产品团队**：详细的季度承诺。
    - **销售团队**：问题和路线的高层次视图。
    - **领导团队**：专注于战略目标和依赖关系。

---

### **产品工具包与模板**

- **工具包的作用**：
    - 提供方法指导，减少工作难度。
- **审查问题**：
    - 当前哪些信息未得到一致分享？
    - 每个模板的受众是谁？
- **示例工具包**：
    - **发现工具包**：
        - 假设测试文档。
        - 用户画像模板。
        - 原型与 A/B 测试工具。
    - **战略工具包**：
        - 战略备忘录。
        - 产品愿景与概要。
        - 战略评审模板。
    - **GTM 工具包**：
        - 发布模板。
        - 产品演示。
        - 入职与培训材料。

---

### **标准化的好处**

- **提高效率**：
    - 提供一致的工具和模板。
- **支持协作**：
    - 通过标准化简化跨团队的沟通和工作流程。

# 第十五章：赋能工具

---

## **工具的作用与限制**

- **工具的误区**：
    - 产品团队可能过度依赖工具，认为“有了这个软件，路线图问题就解决了！”。
- **工具的正确定位**：
    - 工具是用来增强流程和实践的，而不是取代它们。

---

## **跨职能工作组的建立**

- **目标**：
    - 审查、验证并推荐工具。
- **一致的评估流程**：
    - 考虑以下因素：
        - 产品团队和跨职能用户的需求。
        - 工具的实际用例。
        - 实施工具所需的时间与资源。
        - 培训与赋能。
        - 工具采纳的成功率和衡量方法。
        - 成本与预算。

---

## **产品工具堆栈示例**

| **工具类型** | **目标** | **示例** |
| --- | --- | --- |
| **路线图工具** | 切片和展示多视角的路线图。 | ProductBoard, Dragonboat |
| **想法管理工具** | 收集来自利益相关者的最佳想法。 | Aha, Notion |

# 第五部分：在组织中引入产品运营

---

### **初期步骤**

- **目标**：
    - 激发需求，帮助团队了解产品运营的作用。
    - **通过调查**评估组织内部对产品管理价值的认知，并在仪表盘上展示健康指标。

---

### **第十六章：何时以及从哪里开始**

- **产品运营的关键时机**：
    - 当策略变得复杂，工作量增加且难以跟踪时。
- **选择切入点**：
    - 聚焦于组织中最显著的痛点。

---

### **痛点与解决方案**

| **领域** | **痛点** | **产品运营的解决方案** |
| --- | --- | --- |
| **数据与洞察** | 产品经理未创建基于数据的路线图。 | 提供自助访问产品指标的功能。 |
|   | 不清楚研发部门的产出。 | 提供与战略目标对齐的报告功能，优化资源分配。 |
|   | 战略表现难以用数据支持决策。 | 提供量化框架，将业务指标放入产品监控的背景中。 |
| **客户与市场研究** | 销售、支持与用户研究的反馈未传递给团队。 | 改善信息流，帮助团队做出更好的决策。 |
|   | 用户研究难以执行。 | 建立用户访问系统，加速研究流程。 |
|   | 未计算新产品对市场的潜在影响。 | 提供竞争分析和市场规模分析能力。 |
|   | 用户研究未被利用。 | 通过分层和标记用户访谈，将其纳入通用洞察存储库。 |
| **治理与运营模型** | 团队的工作状态缺乏清晰性，难以对齐战略目标。 | 提供与投资组合愿景对齐且易于访问的路线图。 |
|   | 缺乏透明的战略框架来部署产品策略。 | 提供透明且灵活的治理框架，便于扩展和满足需求。 |

---

### **第十七章：争取支持**

- **如何说服利益相关者**：
    - 明确痛点，如：
        - 收入损失。
        - 战略目标延迟。
        - 缺乏定量或定性输入导致输出达不到目标。
- **产品运营的价值**：
    - 通过结果驱动的方法，帮助产品管理扩展并提高效率。

---

### **第十八章：常见反对意见及回应方法**

| **反对意见** | **回应方法** |
| --- | --- |
| 产品经理应独立承担分析工作。 | 支持他们进行战略性工作，同时由分析师提供数据和仪表盘的高质量支持。 |
| 不需要更多的流程和规则。 | 产品运营减少沟通和协作断层，并降低无效流程的风险。 |
| 产品经理已经在与客户沟通。 | 产品运营可确保客户洞察覆盖整个组织，而非局限于少数重复的用户。 |

---

### **第十九章：建立共识**

- **关键观念**：
    - 产品运营团队不做决策，而是**赋能决策的制定**。
- **角色分工**：

| **角色** | **产品经理** | **产品运营经理** |
| --- | --- | --- |
| **职责** | 决策者。 | 提供数据和洞察，支持决策制定。 |
|   | 定义愿景与战略。 | 提供数据支持与沟通帮助。 |
|   | 验证问题与解决方案。 | 支持实验实施与追踪。 |

---

### **第二十章：如何赢得支持**

- **影响力的关键**：
    - 确保向受众传递正确的价值主张。
- **实践建议**：
    - **倾听之旅**：
        - 与 35 位利益相关者交流，识别需求与痛点。
        - 聚焦于每个团队的 1-2 个关键问题，指导产品运营的优先级。
    - **快速成果**：
        - 创建产品通讯以提升可见性。
        - 建立产品发布模板与流程。
        - 闭环跟踪请求，落实后进行反馈。

---

### **第二十二章：启动产品运营**

- **分步实施**：
    - **从小规模开始**：
        - 在一个团队试点，迭代与完善。
    - **建立愿景**：
        - 显示产品运营未来可能的发展路径。
- **成功的产品运营领导者特质**：
    - 以流程为导向，擅长解决复杂问题。
    - 与跨职能领导者协作。
    - 基于数据驱动的决策能力。
- **嵌入式 vs. 集中式模型**：
    - **嵌入式模型**：更定制化，但可能强化孤岛效应。
    - **集中式模型**：更高效，可扩展性更强。

---

### **第三十三章：激活产品运营**

- **三大支柱**：
    1. **业务与数据洞察**。
    2. **客户与市场洞察**。
    3. **流程与实践**。
- **成功衡量标准**：
    - 周期时间、产出量、用户研究周转时间、团队满意度等。
- **启动建议**：
    - 有耐心。
    - 尽早启动，建立基础。
    - 获取跨职能团队的支持。
    - 理解业务需求及痛点。
