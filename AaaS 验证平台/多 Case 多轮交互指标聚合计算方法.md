

> **适用场景**：Agent 评测中，每个 Case 包含多轮模型交互，每个 Case 重复执行多次（如 10 次），最终需要汇总为报告级指标。 **核心挑战**：三层嵌套结构的数据如何正确聚合——不同指标的聚合方式完全不同，用错方式会严重失真。

---

## 一、数据结构：三层嵌套

一个完整的评测数据集是**三层嵌套**的：

```
全部评测集（20 个 Case）
 └── Case-1（SWE-001）
      ├── 第 1 次执行（Run-1）
      │    ├── R1: Planning      → input 2K,  output 500,  TTFT 135ms ...
      │    ├── R2: Read files    → input 4.2K, output 200,  TTFT 215ms ...
      │    ├── R3: Grep          → input 5.5K, output 100,  TTFT 285ms ...
      │    ├── R4: 分析代码       → input 8K,   output 1200, TTFT 420ms ...
      │    ├── R5: 生成修复       → input 12K,  output 2000, TTFT 650ms ...
      │    ├── R6: Write file    → input 14.5K, output 150,  TTFT 740ms ...
      │    ├── R7: 运行测试       → input 16.8K, output 800,  TTFT 870ms ...
      │    └── R8: 输出总结       → input 18.5K, output 300,  TTFT 980ms ...
      ├── 第 2 次执行（Run-2）
      │    └── R1 ~ R9（可能轮数不同）
      ├── ...
      └── 第 10 次执行（Run-10）
           └── R1 ~ R7（可能轮数不同）
 └── Case-2（SWE-015）
      └── Run-1 ~ Run-10
 └── ...
 └── Case-20（ICB-050）
      └── Run-1 ~ Run-10
```

聚合过程分三步走：

```
轮内原始数据 → 跨轮聚合到单次 Run → 跨 Run 聚合到单个 Case → 跨 Case 聚合到报告
```

## 二、第一步：轮内计算——每一轮的原始指标

这是最底层的"原子数据"，每一轮直接可测量，不需要聚合：

|指标|直接测量方式|示例（R5 轮）|
|---|---|---|
|**TTFT**|`T(first_token) − T(request_sent)`|650ms|
|**TPOT**|`(T(last_token) − T(first_token)) / (output_tokens − 1)`|15.2ms/tok|
|**ITL 序列**|`{t₂−t₁, t₃−t₂, ..., tₙ−tₙ₋₁}`|[12, 14, 80, 13, 15, ...]|
|**P99 ITL**|ITL 序列的第 99 百分位|18.5ms|
|**E2E 延迟**|`T(last_token) − T(request_sent)`|31.0s|
|**Prefill 时延**|`T(first_token) − T(infer_start)`|180ms|
|**Decode 时延**|`T(last_token) − T(first_token)`|420ms|
|**input_tokens**|引擎日志直接读取|12,000|
|**output_tokens**|引擎日志直接读取|2,000|
|**工具调用耗时**|`T(tool_end) − T(tool_start)`|280ms|
|**工具调用结果**|pass / fail|✅|

这一步没有任何争议，纯粹是打点采集。

## 三、第二步：跨轮聚合——8 轮 → 1 次 Run 的结果

**这是最关键、最容易犯错的一步。** 不同指标的聚合方式完全不同。

---

### 3.1 TTFT：不做聚合，分拆报告

**❌ 错误做法**：把 8 轮 TTFT 取算术平均。

**为什么错**：TTFT 跟 input_tokens 近似线性——R1（input 2K）的 TTFT 是 135ms，R8（input 18.5K）的 TTFT 是 980ms，平均出来 ~500ms 这个数字毫无意义，既不代表最好情况也不代表最差情况。

**✅ 正确做法**：

```
单次 Run 的 TTFT 输出：
  ├── 首轮 TTFT = R1 的 TTFT = 135ms       ← 用户首次感知
  ├── 末轮 TTFT = R8 的 TTFT = 980ms       ← 最坏情况
  └── 各轮 (input_tokens, TTFT) 散点数据    ← 用于画散点图
```

---

### 3.2 TPOT：按 output_tokens 加权平均

**❌ 错误做法**：8 轮 TPOT 取算术平均。

**为什么错**：R3（Grep，output 100 token，TPOT 10.8ms）和 R5（生成修复，output 2000 token，TPOT 15.2ms），如果算术平均，两轮权重相同。但用户在 R5 等了 30 秒，在 R3 只等了 1 秒——R5 对体验影响大 30 倍。

**✅ 正确做法**：

**公式**：

$$TPOT_{weighted} = \frac{\sum_{r=1}^{8} TPOT_r \times output_tokens_r}{\sum_{r=1}^{8} output_tokens_r}$$

**计算示例**：

```
  R1: 12.1 × 500  =  6,050
  R2: 11.5 × 200  =  2,300
  R3: 10.8 × 100  =  1,080
  R4: 13.6 × 1200 = 16,320
  R5: 15.2 × 2000 = 30,400
  R6: 12.8 × 150  =  1,920
  R7: 14.5 × 800  = 11,600
  R8: 13.2 × 300  =  3,960
  ─────────────────────────
  分子 = 73,630
  分母 = 500+200+100+1200+2000+150+800+300 = 5,250

  加权 TPOT = 73,630 / 5,250 = 14.02 ms/tok
```

**权重分析**：R5（output 最多）对最终结果的贡献权重是 30,400/73,630 = **41.3%**，而 R3（output 最少）的权重仅 1,080/73,630 = **1.5%**。

---

### 3.3 ITL：取各轮 P99 的最大值

**❌ 错误做法**：把 8 轮所有 token 的 ITL 混在一起算 P99。

**为什么错**：混合后，R1-R4 的大量低 ITL token 会"稀释"R5 轮中那个 80ms 的毛刺——用户明明感知到了卡顿，但数据上被掩盖了。

**✅ 正确做法**：

```
每轮单独算 P99 ITL：
  R1: P99 = 15.2ms
  R2: P99 = 13.8ms
  R3: P99 = 12.5ms
  R4: P99 = 16.8ms
  R5: P99 = 18.5ms  ← 最大
  R6: P99 = 14.2ms
  R7: P99 = 17.5ms
  R8: P99 = 15.8ms

max P99 ITL = max(15.2, 13.8, 12.5, 16.8, 18.5, 14.2, 17.5, 15.8)
            = 18.5 ms/tok
```

这个值代表的是"用户在整个任务过程中感知到的最严重卡顿"。

---

### 3.4 E2E 延迟：分层报告，不要简单求和

**❌ 错误做法**：8 轮 E2E 求和当作"任务总时长"。

**为什么错**：轮与轮之间还有 Agent 编排调度的间隙（几十到几百毫秒），还有工具调用的等待时间。简单求和只是"模型推理累计"，不是任务全程。

**✅ 正确做法**：

```
单次 Run 输出三个 E2E：

① AaaS-Latency（任务 E2E）
   = T(task_end) − T(task_start)
   = 132s
   含义：用户感知的完整任务时长

② MaaS-Latency（模型推理累计）
   = Σ(各轮 E2E) = 6.2+2.5+1.3+16.8+31.0+2.6+12.5+5.1 = 78s
   含义：纯模型推理总耗时

③ 非推理开销
   = AaaS-Latency − MaaS-Latency = 132 − 78 = 54s
   含义：工具调用 + Agent 编排 + 网络传输等

④ 推理时间占比
   = 78 / 132 = 59.1%
```

---

### 3.5 Input Tokens：双口径统计

```
① 累计调用量 = Σ(各轮 input_tokens)
   = 2K + 4.2K + 5.5K + 8K + 12K + 14.5K + 16.8K + 18.5K
   = 81,500

② 去重信息量 = 各轮新增内容之和（去除重复的历史上下文）
   ≈ 20,000

③ 膨胀率 = 81,500 / 20,000 = 4.1×
```

---

### 3.6 任务功能正确性：二元判定

```
通过条件（以 Coding 场景为例）：
  ├── Agent 输出了修复 patch                      ✓
  ├── patch 能成功 apply 到代码库                   ✓
  ├── 目标测试（原本 fail 的）现在 pass              ✓
  └── 回归测试（原本 pass 的）仍然 pass              ✓

四项全满足 → 本次 Run = PASS
任一不满足 → 本次 Run = FAIL
```

---

|指标|值|聚合方式|
|---|---|---|
|功能正确性|PASS|二元判定|
|首轮 TTFT|135ms|直接取 R1|

## 四、第三步：跨 Run 聚合——10 次重复 → 1 个 Case 的结论

同一个 Case 跑 10 次，得到 10 张上面的表。现在要汇总成 1 个 Case 级结论。

---

### 4.1 功能正确性：用"多数通过"标准

```
10 次执行结果: [PASS, PASS, PASS, FAIL, PASS, PASS, PASS, PASS, FAIL, PASS]
通过次数: 8/10

判定规则：
  ├── 8/10 ≥ 8  → Case 判定为"通过"
  ├── 同时记录: pass@1 = 80%（单次通过率）
  └── 可选记录: pass@3 = 看连续3次中是否有1次通过
```

**为什么用 8/10 而不是 10/10**：Agent 有一定的随机性（即使 temperature=0，工具调用的返回也可能有差异），10/10 要求过于严苛。8/10 表示"稳定可复现地通过"。

**为什么不用 5/10（简单多数）**：5/10 意味着有一半概率失败，在生产环境不可接受。8/10 是"高置信度通过"。

---

### 4.2 性能指标：取中位数（不是均值）

```
10 次 Run 的加权 TPOT:
  [13.8, 14.2, 13.5, 14.8, 13.9, 14.1, 13.7, 22.5, 14.0, 13.6]
                                              ↑
                                         异常高（可能遇到 GC）

算术平均: 14.81 ms/tok  ← 被异常值拉高
中位数:    13.95 ms/tok  ← 稳定反映典型情况
```

**所有性能指标都取 10 次的中位数**，包括：

- 首轮 TTFT
- 末轮 TTFT
- 加权 TPOT
- max P99 ITL
- AaaS-Latency
- MaaS-Latency

中位数比均值的好处：对偶发抖动（GC、冷启动、网络波动）具有鲁棒性，1-2 次异常不会污染结果。

---

### 4.3 稳定性指标：10 次的变异系数

除了中位数，还要看"10 次之间的波动有多大"：

```
变异系数 CV = std(10 次值) / mean(10 次值) × 100%

判定标准：
  CV < 5%   → 非常稳定（绿灯）
  5-15%     → 正常波动（黄灯）
  CV > 15%  → 不稳定，需排查（红灯）
```

---

### 4.4 资源消耗：取中位数或均值均可

```
10 次 Run 的总轮数: [8, 8, 8, 9, 8, 8, 8, 10, 8, 8]
中位数: 8 轮

10 次 Run 的累计 input tokens: [81500, 81500, 81500, 92000, 81500, ...]
中位数: 81,500 tokens
```

如果 10 次中有某次轮数异常多（比如 10 轮），说明 Agent 走了弯路，需要额外轮次纠正——这本身就是一个诊断信号。

---

### 4.5 单个 Case 的完整输出

|指标|值|聚合方式|
|---|---|---|
|**Case 通过判定**|PASS（8/10）|≥ 8 次通过|
|**pass@1**|80%|10 次中通过的比例|
|**首轮 TTFT**|135ms|10 次中位数|
|**末轮 TTFT**|980ms|10 次中位数|
|**加权 TPOT**|13.95 ms/tok|10 次中位数|

## 五、第四步：跨 Case 聚合——20 个 Case → 报告级汇总

现在有 20 个 Case，每个 Case 都有上面那张表。最后一步是汇总成报告正文的指标。

---

### 5.1 任务完成率：简单计数

```
通过的 Case 数 / 总 Case 数 = 19 / 20 = 95%

也可以用更精细的 pass@1 均值:
  mean(各 Case 的 pass@1) = mean(80%, 100%, 90%, ...) = 92.5%
```

---

### 5.2 性能指标汇总：三种方式

**方式 A：简单中位数**——把 20 个 Case 的中位 TPOT 排序取中间值。

```
20 个 Case 的加权 TPOT（各自已是 10 次中位数）:
  [12.5, 13.2, 13.8, 13.9, 14.0, 14.1, 14.2, 14.5, 14.8, 15.0,
   15.2, 15.5, 15.8, 16.0, 16.2, 16.5, 17.0, 17.5, 18.0, 19.2]

中位数 = (15.0 + 15.2) / 2 = 15.1 ms/tok
```

**方式 B：按 output_tokens 再次加权**——困难 Case 的 output 更多，权重更大。

$$TPOT_{report} = \frac{\sum_{i=1}^{20} TPOT_{case_i} \times output_tokens_{case_i}}{\sum_{i=1}^{20} output_tokens_{case_i}}$$

**方式 C：分层报告（推荐）**——按难度分组各报一个：

|难度|Case 数|中位 TPOT|中位 AaaS-Latency|通过率|
|---|---|---|---|---|
|简单|6|12.8 ms/tok|68s|100%|
|中等|8|14.5 ms/tok|132s|98.8%|
|困难|6|17.2 ms/tok|285s|96.7%|
|**全部**|**20**|**14.5 ms/tok**|**132s**|**95%**|

**推荐做法**：报告正文用方式 C（分层 + 全局），附录用方式 A 给出每个 Case 的原始数据。

---

### 5.3 百分位分布：拉平全部数据

这个聚合方式比较特殊——把所有 Case 的所有 Run 的所有轮次的数据**全部拉平**成一个大数组，然后取百分位。

```
数据来源:
  20 个 Case × 10 次 Run × 8 轮 = 1,600 个 TTFT 数据点

全部拉平后排序，取百分位:
  P50 =  95ms
  P75 = 120ms
  P90 = 142ms
  P99 = 380ms
  max = 520ms
```

这就是报告模板 §5.3 "百分位性能分布"中那张表的计算方式。拉平是合理的，因为百分位分布关心的是"所有请求中最差的 1% 表现如何"，不区分 Case。

## 七、关键原则速查表

|原则|说明|
|---|---|
|✗ 不要对 TTFT 跨轮取算术平均|TTFT 是 input_tokens 的函数，不同轮 input 差 9 倍，平均无意义|
|✗ 不要对 TPOT 做等权平均|重轮次（output 多）对用户体验影响远大于轻轮次|
|✗ 不要对 ITL 跨轮混合|大量低 ITL token 会稀释少数高 ITL 毛刺，掩盖卡顿|
|✗ 不要对性能指标跨 Run 取算术平均|偶发异常值（GC、冷启动）会拉偏均值，用中位数更鲁棒|
|✗ 不要把各轮 E2E 求和当任务时长|轮间有编排间隙和工具等待，需用墙钟时间|
|✗ 不要把累计 input tokens 当"信息量"|含大量重复上下文，需同时报去重信息量和膨胀率|
|✓ 永远保留下钻路径|汇总 → Case 明细 → Run 明细 → 轮明细，任何层级可追溯|
|✓ TTFT 用散点图而非单一数字|展示 TTFT 随 input_tokens 增长的趋势|
|✓ 正确性用 8/10 多数通过标准|排除偶发成功/失败的噪声，高置信度判定|
|✓ 报告正文用分层汇总|按难度/类型分组，暴露结构性短板|
