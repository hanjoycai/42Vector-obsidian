推理效率与性能验证指标

定位：这里汇总两大数据指标：推理过程中Maas和 Agent 可观测链路的多个数据源，汇总后统一统计

说明：以下指标均建立在 Agent 在特定场景下的特定任务所输出的关联性时序结果

### 单一任务端到端测试

**【体验指标】**聚焦于从用户输入请求到最终输出结果的全流程验证。通过模拟真实业务场景下的用户交互，覆盖从初始请求接收、模型推理、工具调用到结果返回的完整链路，综合评估智能体在不同硬件环境下的性能表现

### 4.2 并发任务端到端测试-综合性能测试

**【体验指标】**重点解决Agent 运行过程中在给定并发和请求规模下，整体吞吐、成功率、平均时延、首 token 响应和单 token 生成效率是否达标。直接量化Agent单次任务的综合表现，帮助快速判断：当前硬件和推理链路能不能支撑真实业务负载，瓶颈是在性能、稳定性还是承载能力。

| **总吞吐量** | 每秒处理的平均总 token 数（输入+输出） | token/s | 并发测试期间所有请求平均每秒处理的总 token 数（输入 + 输出），综合衡量集群处理能力 | 总吞吐量 = Σ(各成功请求 input_tokens + output_tokens) / 测试总时长 | Prometheus 聚合 vllm:prompt_tokens_total + vllm:generation_tokens_total 的 rate，或自行计算 | 客户用此计算"服务 N 个并发 Agent 任务需要多少节点"，直接驱动采购规模和集群容量规划决策 |

| **有效吞吐量 (Goodput)** | 仅成功请求的输出 token 吞吐 | token/s | 仅统计成功完成请求产生的输出 token 吞吐。排除失败、超时、被抢占请求产生的无效 token，是经济意义上真正有价值的产出 | Goodput = Σ(成功请求的 output_tokens) / 测试总时长 | ① Prometheus 成功请求 token counter rate<br>② Opik 成功 Trace 的 token 聚合计算 | Goodput 与总吞吐量的差值 = 浪费的算力。差值越大说明并发下资源利用越低效，芯片调度和内存架构需优化 |
| **超时请求数** | 因超过预设等待时间而终止的请求数 | 个 | 因等待时间超过预设超时阈值（如 30s/60s）而强制终止的请求数量。区别于模型推理错误——超时通常反映排队过深或计算资源不足 | 累计 error_type=timeout 的请求数 | ① LiteLLM 错误日志中 timeout 类型计数<br>② Prometheus request_timeout_total counter | 超时是并发过载的典型信号——超时率突增意味着需要扩容或降低并发，客户据此设置合理负载上限 |
| **限流/拒绝请求数** | 被系统限流或拒绝的请求数 | 个 | 被推理引擎或网关因负载保护策略主动拒绝（HTTP 429 Too Many Requests / 503 Service Unavailable）的请求数量 | 累计 HTTP 429 或 503 响应的请求数 | ① LiteLLM 错误日志中 status=429/503 计数<br>② Prometheus request_rejected_total counter | 量化系统容量边界——限流数突增说明已达系统承载极限，客户据此规划冗余容量和弹性扩缩策略 |
| **错误类型分布** | 各类错误的占比分布 | — | 将所有失败请求按错误类型（超时、OOM、限流 429、推理错误 500、网络异常等）分类统计的占比分布，用于精准定位失败根因 | 各错误类型数量 / 失败总数 × 100%，输出分布表格 | ① LiteLLM 错误码分类聚合<br>② Prometheus request_failure_total 按 error_type label 分组 | 定位失败根因——OOM 多说明显存不足需换更大显存卡，超时多说明算力不足，限流多说明需扩容。帮助客户精准投资 |
| **平均排队等待时间** | 并发下请求在调度队列中平均等待时间 | ms | 并发负载下所有请求在推理引擎调度队列中排队等待开始处理的平均时间。是 TTFT 中非计算部分，反映资源饱和程度 | 平均排队时间 = mean(各请求的 TTFT − Prefill_time) | ① Prometheus vllm:request_queue_time histogram<br>② 基于 TTFT 和 Prefill 时间差自行计算 | 排队时间是并发下最敏感的退化指标——直接量化"芯片处理不过来的程度"，指导扩容和调度优化决策 |
| **KV Cache 使用率峰值** | 并发期间 KV Cache 使用的最高比例 | % | 并发测试期间 KV Cache 占用显存达到的最高比例。峰值接近 100% 意味着后续请求将被拒绝、驱逐或抢占 | KV Cache 峰值 = max(采样周期内 kv_cache_usage%) | ① Prometheus max_over_time(vllm:gpu_cache_usage_perc[测试时长])<br>② Maas 引擎监控峰值 | 并发下显存压力顶点——峰值 >95% 说明长上下文或高并发场景下极易触发 OOM 或抢占，客户需更大显存或优化 KV Cache 策略 |
| **被抢占请求数** | 并发期间被调度器抢占的请求数 | 个 | 并发测试期间被推理引擎调度器抢占（暂停正在处理的请求以释放显存给新请求或更高优先级请求）的累计数量 | 累计计数，counter 类型 | ① Prometheus vllm:num_requests_swapped counter<br>② Maas 调度日志 | 抢占率 = 并发下显存争用的直接证据。高抢占意味着请求被反复暂停/恢复，增加延迟并浪费已有计算 |
| **并发扩展效率** | 吞吐量随并发数增长的线性度 | — | 衡量系统吞吐量随并发数增加的扩展能力。理想线性扩展 = 100%，实际因调度开销和资源争用会衰减。需基于多组并发梯度（如 1/2/4/8/16/32）测试 | 扩展效率 = (并发N的吞吐量 / 并发1的吞吐量) / N × 100% | 基于 4.1 单任务 + 4.2 多组并发测试结果的吞吐量对比计算 | 芯片调度架构的核心竞争力——线性度高说明芯片 + 引擎在并发下保持高效，客户可用更少节点支撑更大负载，直接降低 TCO |
| **SLA 达标率** | 满足预设 SLA 阈值的请求比例 | % | 在预设 SLA 阈值下（如 P99 E2E <500ms、TTFT <200ms），满足全部 SLA 条件的请求占总请求的比例 | SLA 达标率 = 满足全部 SLA 条件的请求数 / 总请求数 × 100% | 基于 LiteLLM/Opik 各请求延迟数据与 SLA 阈值对比计算 | 直接回答客户最关心的问题："我的 SLA 能保住吗？"——达标率 <99.9% 意味着芯片在该并发下无法满足生产需求 |
| **性能衰减系数** | 并发 vs 单任务的性能退化比 | — | 并发测试中关键指标（TTFT / TPOT / E2E Latency / 吞吐量）相对 4.1 单任务结果的退化幅度。量化并发带来的性能代价 | 衰减系数 = 并发N指标值 / 单任务指标值（延迟类 >1 表退化；吞吐类 <1 表退化） | 对比 4.1 单任务结果和 4.2 并发结果，逐指标计算 | 量化并发代价——TTFT 衰减 3× 意味着并发下首 token 慢 3 倍。客户据此评估真实负载下用户体验退化幅度，决定是否可接受 |
| **多模型共置效率** | 同一节点同时部署多个模型时的总吞吐保持率 | % | 同一节点同时部署多个模型（如 7B 路由模型 + 72B 执行模型）时，各模型总吞吐量相对独占部署时吞吐总和的保持比例。受显存争用和调度开销影响，通常 70-85% | 共置效率 = Σ(共置时各模型吞吐) / Σ(独占时各模型吞吐) × 100% | 分别测试独占和共置场景的吞吐量，对比计算 | KA 客户通常多模型混合部署——共置效率低意味着需要更多节点，直接增加采购成本 |
| **租户间性能隔离度** | 多租户共享推理实例时的性能保持率 | % | 多租户共享同一推理实例时，单租户性能相对独占时的保持比例。隔离度低意味着"邻居噪声"干扰严重——某租户突发大请求导致其他租户延迟飙升 | 隔离度 = 共享时单租户 P99 延迟 / 独占时单租户 P99 延迟（越接近 1 越好） | 模拟多租户场景：一个租户持续突发负载，观测其他租户的 P99 延迟变化 | 多租户部署的公平性保证——隔离度 <80% 意味着租户体验不可控，需要引擎层面的资源隔离或独占部署 |
| **峰值负载后恢复时间** | 突发高并发结束后系统恢复正常的时间 | s | 突发高并发（如 10× 正常流量）结束后，系统吞吐量和延迟恢复到正常水平（±10%）的时间。反映引擎的弹性回弹能力和资源释放效率 | 恢复时间 = T(指标恢复正常) − T(峰值负载结束) | 压测工具控制流量波形（正常→峰值→正常），监控 Prometheus 指标恢复时间点 | 弹性回弹能力——恢复时间长说明资源被"锁死"（如 KV Cache 未及时释放），影响后续请求的正常服务 |

#### 4.2.1 Agent 并发专项指标

**【Agent 并发体验指标】**上表聚焦模型推理请求级的并发性能。但 Agent 任务通常包含多轮模型调用 + 工具调用的复杂编排链路，当多个 Agent 任务同时运行时，会产生推理请求级指标无法捕获的"Agent 级并发效应"——如多 Agent 抢占 KV Cache 导致上下文被驱逐、工具调用阻塞导致推理连接占用时间增长、以及 Agent 交互轮数因排队而被迫增加等。以下指标从 Agent 任务粒度出发，评估多 Agent 并行时的整体效率和可靠性。

| **指标** | 解释 | 单位 | 指标定义 | 计算公式 | 取数来源 | 指标价值 |
| --- | --- | --- | --- | --- | --- | --- |
| **Agent 并发任务数** | 同时运行的 Agent 任务数量 | 个 | 测试中同时发起的 Agent 端到端任务数量（非模型请求并发数）。每个 Agent 任务内部包含多轮模型调用和工具调用，N 个 Agent 并发产生的实际模型请求并发远大于 N | 由测试配置指定，如 concurrent_agents = N | AaaS 平台并发测试配置 | 区分"模型请求并发"和"Agent 任务并发"——客户真正关心的是"能同时跑多少个 Agent"，而非底层有多少请求 |
| **Agent 任务成功率（并发）** | 并发下 Agent 任务成功完成的比例 | % | 多 Agent 并发运行时，成功完成全部步骤并产出正确结果的 Agent 任务占比。并发下可能因排队超时、KV Cache 驱逐导致上下文丢失而任务失败 | 并发成功率 = 并发下成功 Agent 任务数 / 并发总 Agent 任务数 × 100% | AaaS 平台并发测试的 Agent 任务状态统计；Opik 并发 Trace 成功率 | Agent 级可靠性——与 4.3 单任务成功率对比可揭示并发带来的额外失败。客户据此判断芯片能同时支撑的 Agent 规模 |
| **Agent 任务平均耗时（并发）** | 并发下 Agent 完成任务的平均用时 | min | 多 Agent 并发运行时，从任务接收到最终输出的平均用时。并发下因排队和争用，耗时通常显著增加 | 并发平均耗时 = Σ(并发下各 Agent 任务完成时长) / 完成任务数 | Opik 并发 Trace 根节点 duration 均值；AaaS 平台统计 | 与 4.3 单任务耗时对比，量化并发带来的耗时膨胀——膨胀率过高意味着需要扩容或优化调度 |
| **Agent 首轮响应时间（并发）** | 并发下 Agent 第一轮模型调用的响应时间 | ms | 多 Agent 并发时，每个 Agent 从发起第一轮模型调用到获得首次完整响应的平均时间。反映用户"发出任务后多久感知到 Agent 开始工作" | Agent 首轮响应 = mean(各 Agent 第一个 LLM span 的 E2E latency) | Opik 并发 Trace 中各 Agent 根 Trace 下第一个 LLM span 的 duration | 用户感知的 Agent "启动速度"——并发下首轮延迟过高意味着用户会认为"系统没反应"，直接影响产品体验 |
| **Agent 多轮推理累计排队时间** | Agent 任务内所有模型调用的排队等待时间总和 | ms | 一个 Agent 任务全链路中，所有模型调用在推理引擎中排队等待的时间累计。Agent 多轮调用（如 5-20 轮）会放大排队效应 | 累计排队时间 = Σ(Agent 内各 LLM 调用的排队等待时间) | 基于各 LLM span 的 TTFT − Prefill_time 求和 | Agent 场景的排队放大效应——单次排队 50ms 在 10 轮交互后累积为 500ms，占总耗时的显著比例。揭示排队对 Agent 的真实影响 |
| **Agent 交互轮数增加率** | 并发下 Agent 完成任务所需轮数相比单任务的增加比例 | % | 多 Agent 并发时，因推理延迟增大可能触发超时重试、工具调用失败重试等，导致完成同一任务需要更多交互轮数 | 增加率 = (并发下平均轮数 − 单任务平均轮数) / 单任务平均轮数 × 100% | 对比 4.3 单任务平均交互轮数与并发下 Opik Trace LLM span 数量 | 轮数增加 = 隐性成本膨胀。每增一轮意味着额外的 input + output token 消耗和延迟，但不体现在单请求指标中 |
| **Agent 工具调用并发阻塞率** | 并发下工具调用因资源争用而阻塞或失败的比例 | % | 多 Agent 同时调用外部工具（MCP/API/数据库等）时，因连接池耗尽、API 限流、资源锁等导致工具调用阻塞或失败的比例 | 阻塞率 = (阻塞/失败的工具调用数) / 总工具调用数 × 100% | Opik Trace 中 tool_call span 的 error/timeout 状态统计 | 工具调用是 Agent 区别于纯 LLM 的核心特征。工具并发争用会导致 Agent 任务链断裂，暴露系统在 Agent 负载下的工具层瓶颈 |
| **Agent 上下文膨胀率** | 并发下 Agent 输入 token 数相比单任务的增长比例 | % | 并发场景中因重试、错误恢复、额外上下文注入等导致 Agent 各轮模型调用的平均输入 token 数相比单任务时的增长比例 | 膨胀率 = (并发下平均 input_tokens − 单任务平均 input_tokens) / 单任务平均 input_tokens × 100% | 对比 4.3 单任务输入 token 均值与并发下 Opik 各 LLM span 的 input_tokens 均值 | 上下文膨胀 = Prefill 负载加重 + 成本增加。膨胀率高说明并发下 Agent 需要更多上下文来补偿错误恢复，加剧显存和成本压力 |

### 4.4 Agent 任务运行时指标

**【诊断指标-底层定位】**主要是帮助观测并了解单次 Agent 请求在运行过程中到底经历了什么、慢在哪里、资源卡在哪里。

  核心解决：模型请求进入后，模型输入输出参数是否合理，推理过程每一段耗时是否正常，引擎侧有没有排队、抢占、缓存命中不足等问题。帮助进一步拆解参数问题、模型推理问题、调度排队问题、引擎资源问题，让团队能快速判断到底该优化模型配置、推理链路，还是芯片资源利用和引擎调度策略，从而快速定位性能瓶颈。

| **推理过程层级** | **结果** | 指标定义 | 计算公式 | 取数来源 | 指标价值 |
| --- | --- | --- | --- | --- | --- |
| **内部接口** | 任务编码 | 单次 Agent 请求的唯一追踪标识（trace_id / request_id），用于关联该请求在推理全链路各阶段的所有数据 | 由系统自动生成，UUID 或 trace_id 格式 | Opik Trace ID；Maas 请求 request_id | 支持单请求全链路追踪和故障定位，出问题时可快速回溯完整推理过程 |

### 4.5 百分位性能指标测试

- 暴露系统稳定性瓶颈

- 直观展示硬件架构差异对性能的影响

### 4.7 芯片适配与长稳验收指标

**【交付验收指标】**本章节指标回答的不是"芯片性能怎么样"，而是"芯片能不能用、稳不稳、生态行不行"。这是国产芯片（摩尔线程、寒武纪、沐曦、昇腾等）交付 KA 客户时最先被验证、也是差距最大的维度。根据 MLPerf 测试数据，国产芯片驱动崩溃率约 23%（NVIDIA 仅 0.3%），关键算子缺失导致性能下降 40-60%。以下指标聚焦芯片生态成熟度、模型适配能力和长期运行稳定性，是客户验收和生产部署的前置必要条件。

**指标价值：**

- **回答客户第一个问题：我的模型能不能跑起来？（算子覆盖、模型迁移、精度对齐）**

- **回答客户第二个问题：跑起来之后稳不稳？（MTBF、长稳、崩溃率、MTTR）**

- **回答客户第三个问题：生态能不能用？（框架兼容、MLPerf 达标）**


| 指标 | 单位 | 指标定义 | 计算公式 | 取数来源 | 指标价值 |
| --- | --- | --- | --- | --- | --- |
| **算子覆盖率** | % | 推理引擎所需全部算子（包括标准算子和融合算子）中，芯片软件栈原生支持且性能达标的比例。关键算子（如 FlashAttention-2、RMSNorm、RotaryEmbedding）缺失可能导致性能骤降 40-60% | 算子覆盖率 = 已支持算子数 / 模型所需总算子数 × 100%，需区分"支持"和"性能达标" | 芯片厂商软件栈文档；模型转换工具的算子兼容性报告；AaaS 平台模型适配测试 | 国产芯片最核心的生态指标——覆盖率 <95% 意味着需要大量手动算子替换和性能调优，客户迁移成本极高 |
| **模型迁移适配率** | % | 目标模型从 NVIDIA GPU（PyTorch/vLLM）迁移到自研芯片后，不修改或仅少量修改代码即可正常运行和通过精度校验的成功率 | 适配率 = 成功迁移并通过精度校验的模型数 / 总测试模型数 × 100% | AaaS 平台模型适配测试模块；芯片厂商迁移工具日志 | 客户的基础期望是"一键迁移"——适配率低意味着每个模型都需要专项适配工作，延长交付周期、增加人力成本 |
| **精度对齐率（跨芯片 FP32 基准）** | % | 自研芯片上模型推理输出与 NVIDIA GPU（FP32 精度）的逐 token 一致性比例。区别于 4.3 的"Token 精度"——这里强调的是跨芯片横向对齐 | 精度对齐率 = 与 NVIDIA FP32 输出一致的 token 数 / 总 output_tokens × 100% | AaaS 平台跨芯片精度对比测试模块 | 客户需要确认"同一个模型在你的芯片上跑出来的结果和在 A100 上一样"——对齐率 <99% 需要排查芯片数值精度问题 |
| **MTBF（平均无故障时间）** | 小时 | 芯片及推理服务栈在持续推理负载下的平均无故障运行时长。包含芯片硬件故障、驱动崩溃、推理引擎异常、OOM 等全部故障类型 | MTBF = 总运行时长 / 故障次数 | 长稳测试日志中的故障事件记录；Prometheus 进程重启 counter；系统 dmesg/journalctl 日志 | KA 客户要求 MTBF >720h（30天）。搜索显示国产芯片 MTBF 显著低于 NVIDIA，是客户最担心的指标，直接决定是否敢在生产环境使用 |
| **7×24h 长稳测试通过率** | % | 连续 7 天 24 小时不间断推理负载下，成功完成全部请求且性能无显著退化的比例。暴露内存泄漏、显存碎片化、KV Cache 碎片、热节流累积等长期运行问题 | 长稳通过率 = 长稳测试中正常完成的时间段 / 总测试时长 × 100%（以小时为粒度） | AaaS 平台长稳测试模块；Prometheus 全程监控数据 | 客户买芯片是 7×24 不停机运行——5 分钟压测满分但 48h 后崩溃 = 不合格。长稳测试是生产部署的前置硬门槛 |
| **驱动/软件栈崩溃率** | 次/24h | 推理服务运行过程中因芯片驱动、固件、编译器、运行时库等软件栈问题导致的崩溃次数，按 24 小时标准化 | 崩溃率 = 软件栈相关崩溃总次数 / 运行总天数 | Prometheus 进程重启 counter；系统 dmesg OOM/Segfault/GPU Reset 日志；AaaS 异常事件日志 | 国产芯片的关键短板——MLPerf 数据显示国产芯片崩溃率约 23% vs NVIDIA 0.3%。客户要求 <0.1 次/24h 才考虑生产部署 |
| **故障恢复时间 MTTR** | s | 推理服务从崩溃（进程异常退出、GPU Reset 等）到自动恢复并重新接受请求的平均时间。包含进程重启、模型重新加载、KV Cache 重建等环节 | MTTR = Σ(各次故障恢复耗时) / 故障次数 | AaaS 平台故障恢复日志；Prometheus 服务健康检查恢复时间戳 | 生产级要求 MTTR <30s。MTTR 长意味着每次崩溃都造成长时间服务中断，对 SLA 影响巨大 |
| **长时间运行性能衰减率** | %/h | 连续运行 N 小时后，吞吐量和延迟指标相对初始值的退化幅度（按小时标准化）。衰减来源包括显存泄漏、KV Cache 碎片化、热节流累积等 | 衰减率 = (初始吞吐量 − N小时后吞吐量) / 初始吞吐量 / N × 100% | 长稳测试中每小时采样的吞吐量和延迟时序数据 | 衰减率 >1%/h 说明存在严重的长期运行问题——72 小时后性能下降 >72% 不可接受。客户需要"跑多久都一样快" |
| **显存碎片率** | % | 长时间运行后加速卡显存碎片化程度。碎片率高会导致"显存总量够但分配不出连续块"，触发 OOM 或 KV Cache 驱逐 | 碎片率 = 1 − (最大可分配连续块 / 总空闲显存) × 100% | 推理引擎内部 memory allocator 统计；Prometheus 自定义 metrics | 国产芯片的典型长稳问题——显存碎片导致"幽灵 OOM"（显存看起来够但实际分配失败），是长稳测试中最难排查的问题之一 |
| **生态兼容性评分** | — | 对 PyTorch、vLLM、TensorRT-LLM、Triton Inference Server、SGLang 等主流推理框架和工具链的兼容支持程度综合评分（如 5 分制：完全兼容/基本兼容/需适配/部分支持/不支持） | 按框架逐一评估兼容性等级，加权平均得综合分 | AaaS 平台生态兼容性测试模块；芯片厂商文档和社区支持度评估 | 客户不接受"只能用厂商自己的框架"——昇腾 CANN 文档完整性仅 CUDA 60%，客户需要评估迁移后的工具链可用性 |
| **MLPerf 场景达标声明** | Pass/Fail | 是否在 MLPerf 官方基准测试中提交并通过 Server / Interactive / Offline 场景验证。MLPerf v6.0（2026.4）已有 24 家组织参与提交 | 以 MLPerf 官方公布的提交结果为准，Pass = 已提交且通过；Fail = 未提交或未通过 | MLCommons 官网 MLPerf Inference 结果页面（公开数据） | 第三方公信力——MLPerf 是行业唯一被广泛认可的推理基准。KA 客户（运营商、金融）在采购评审中会直接要求提供 MLPerf 成绩单 |
