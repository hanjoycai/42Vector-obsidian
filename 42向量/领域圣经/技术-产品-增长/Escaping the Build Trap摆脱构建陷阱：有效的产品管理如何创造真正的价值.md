## 什么是构建陷阱（Build Trap）？

当产品团队忘记了什么能驱动价值，而是专注于并庆祝发布功能时，就会陷入构建陷阱。他们用输出（outputs）而非结果（outcomes）来衡量成功。团队的关注点逐渐从为客户创造价值和为企业实现价值，转移到发布功能和完成项目上。

团队将输出置于结果之上。输出是一些容易量化的事物，例如我们生产的产品数量、功能、版本发布以及开发速度。

### 构建陷阱的警示信号 🚩

- 用户研究被忽略，转而专注于构建更多东西
- 路线图不切实际，项目过多
- 截止日期和功能比客户指标更重要
- 新功能未被使用，未带来结果。产品臃肿，但人们仍然庆祝发布
- 团队感觉无法中止项目，转而专注于更有意义的事情
- 团队成员对什么是最重要的事情未达成一致
- 团队中缺乏强有力的产品管理
- 与客户沟通、研究和实验被认为是在浪费时间
- 团队不了解战略或愿景

### 如何逃离构建陷阱？

- 成为以产品为导向的团队
- 将关注点从构建功能转移到实现结果
- 为产品经理（PMs）提供更多空间，寻找最大化业务和客户价值的机会
- 问题可能在某些组织中根深蒂固，因此需要准备思考以下方面：
    - 个人激励
    - 公司文化
    - 团队结构
    - 产品战略
    - 公司政策
    - 团队流程
    - 团队个体

### 价值交换系统

从根本上来说，一家公司是通过价值交换而存续的。他们提供产品或服务，帮助客户解决问题/满足需求，并从中获取一部分价值回报。这种价值通常是货币，但也可能是数据、知识、宣传等。

产品团队应专注于为客户创造价值，帮助解决问题/满足需求。要有效做到这一点，你需要了解你的客户及其问题/需求。

很容易被干扰并失去焦点。快速跟随竞争对手、构建销售团队建议的功能，或者迎合老板的意愿，都是常见的诱惑。

你和你的客户是复杂适应系统的一部分，他们的需求在变化，你的机会和应对方式也在变化。你无法控制或预测他们，最好的策略是理解他们。

企业是复杂的，可能会阻碍自己的发展。要避免创建僵化的开发流程和节奏，这会限制实验的空间。思考人员、流程、政策、战略和文化。优化输出很容易，但也很容易陷入“仅关注输出”的模式。

## 产品经理的角色

产品经理了解业务和客户，能够识别创造价值的正确机会。他们综合多方面的数据，确定团队应前进的方向。

**关键数据来源**：用户分析 · 客户反馈 · 市场研究 · 利益相关者意见

他们让团队专注于“为什么”——为什么我们要构建这一产品？它将产生什么结果？

**不要为了避免与工程师沟通而创建详尽的产品需求文档（PRDs）。**

### 关于敏捷和瀑布式开发

许多产品经理以瀑布式方法操作或至少学习过这种方法：

采集利益相关者输入 → 转化为规格说明 → 转交给设计团队进行UI设计 → 转交给开发人员 → 发布给客户。

敏捷并不是创造更多价值的灵丹妙药。它促进了更好的协作和更快速的构建，但忽略了如何进行有效的产品管理。**敏捷假设在前端漏斗中有人在生成和验证想法，但这并不足够。**

| **不良产品经理类型** | **如何避免他们的特点** |
| --- | --- |
| 小型CEO | 选择影响力而非权威。<br>选择创造价值而非仅执行自己的想法。<br>选择倾听并让团队参与。<br>选择爱上问题（而非解决方案）。<br>选择通过数据反驳自己的想法。 |
| 侍者型产品经理 | 不要盲目优先考虑利益相关者、客户和经理的请求。<br>选择有愿景、有目标（更容易优先排序）。<br>避免产品死亡循环：没人用产品 → 询问用户缺少什么功能 → 构建缺失的功能（想法未经验证）。<br>不要向客户寻求解决方案，而是选择理解他们的问题。 |
| 前项目经理型 | 产品经理负责“为什么”，而非“何时”。<br>回答“为什么”和回答“何时”不同，需要保持战略思维。 |

## 优秀的产品经理

- **平衡业务需求和解决用户问题**
    - 他们找到与业务目标一致的用户问题/需求。
    - 他们努力理解产品团队目标如何契合业务目标。
- **理解并与其他学科合作，从他们的技能和专业中获取最大收益**
    - 他们利用其他学科的集体知识，定期将其纳入以建立对问题的共同理解。
    - 产品经理是影响者，而非管理者。他们与他人合作，发挥他人的长处。
    - 产品经理不应孤军奋战，而应与团队一起生成解决方案并探索问题。
    - 产品经理需要掌握技术、商业和设计知识，能够讨论关键权衡，提出正确的问题。
    - 产品经理平衡各学科的优先级，制定策略，决定对产品最有利的选择。
- **连接多种输入，理清关键点**
    - 他们筛选信息，创造一个产品愿景，推动公司前进并解决客户需求/问题。
    - 理解商业模式和市场。
    - 理解公司的愿景和目标。
    - 与用户体验不同——产品经理超越体验，关注整个系统：
        - 需求、功能组成、价值主张、用户体验、底层商业模式、定价、集成、收入来源等。
- **对用户怀有深切的同理心**
    - 他们付出努力去理解用户的问题、需求。
- **始终关注问题——锚定在“为什么”，增加构建正确事物的可能性**
    - 产品经理需要识别下一个最重要的事情，并说服利益相关者。
- **掌握并传达“为什么”**
    - 他们知道目标，理解方向。
    - 他们构建产品愿景，进行沟通并推动其实现。
- **通过实验寻找最佳解决方案**
    - 他们与团队从愿景开始，确定合理的第一步。
    - 在实施前验证愿景。
    - 与团队一起开发和测试想法。
    - 确保其实现客户、用户和业务目标。
- **保持谦逊**
    - 认识到自己不知道答案。他们需要解决假设问题。
    - **产品经理通过专注于学习来降低风险。他们知道并非所有的好想法都来自自己。**

### 产品生命周期影响优先级

- **早期阶段** - 确定最重要的问题
- **中期阶段** - 找出解决问题的方法（构建什么）
- **后期阶段** - 确定是否解决了问题

### 产品工作的类型

| **类型** | **描述** |
| --- | --- |
| **战术型** | 短期目标。将功能推向市场。为开发人员和设计师分解任务。 |
| **操作型** | 将战略与战术工作联系起来。创建一条路线图，将产品的当前状态与未来状态联系起来，使团队围绕工作展开一致行动。 |
| **战略型** | 将产品和公司定位于市场中以取得成功并实现目标。关注产品和公司的未来，以及如何实现目标。 |

随着职位晋升，你会更多地从事战略型工作，减少战术型工作。

### 不同资历水平的产品角色

| **职位** | **职责与描述** |
| --- | --- |
| **初级产品经理** | 从这里开始。如果需要转换角色，也从这里开始。更多公司应该设立这个职位。配对资深产品经理来教导他们。给予他们所需的指导。通过给予新人机会，创造你所需要的资深人才。 |
| **产品经理** | 为用户设计并构建正确的解决方案（与工程和设计团队一起）。与用户交流。综合数据。对功能做出决策。具备一定的战略能力以制定功能愿景，了解功能如何融入产品。足够战术化以确保执行顺畅。更偏向操作型而非战略型。职责通常集中于短期影响和功能交付。季度时间跨度。如果过多关注战术工作，将在战略和愿景工作上落后。还需要向更高级别的产品经理提供数据。如果你称这个角色为产品负责人（PO），你就忽略了战略部分，把功能工作与产品愿景联系起来。 |
| **高级产品经理** | 与产品经理职责相同，但范围更广或更复杂。仍然是个体贡献者。平衡高战略性和操作性。适合喜欢解决复杂产品问题的人。具有创业特质。 |
| **产品总监** | 对于团队扩展很重要——当产品团队报告人数太多时。产品范围和进行中的工作（WIP）增加。战略对齐+操作效率。将产品与产品组合愿景联系起来。人员管理——监督产品组合或产品线中的产品经理。负责战略产品路线图。一年时间跨度。团队的操作效率。<使产品经理与目标对齐，专注于最重要的事情。 |
| **产品副总裁** | 负责整个产品线的战略和运营。将公司目标与产品线增长目标联系起来。为产品设定愿景和目标。负责产品线的财务成功，不仅仅是功能交付。将战略与目标对齐到产品组合中。具有创业精神——擅长启动和发展新产品。成功的产品副总裁更注重战略，雇佣他人执行战术工作。 |
| **首席产品官** | 负责公司的整个产品组合——在执行委员会层面工作。公司新增第二个产品时通常会设立该职位。通过产品组合推动业务的经济成功。与董事会对接。激发信心（在愿景中），与团队同理并保持韧性和坚韧。 |

> ### 围绕价值而非API组织团队
> 
> **TL;DR** 不要围绕API或技术组织团队。根据目标（如果团队小），或根据价值流（如果团队大）组织团队，以优先考虑传递价值。
> 
> **不要围绕API或技术组织团队。**
> 
> - 一旦API被构建，切换到监控和支持模式，让团队继续开展其他工作。
>     - **理由**：稳定的API不应需要团队持续工作。
>     - **否则**：你将没有足够的资源解决更大的问题。
>     - **否则**：团队将因低优先级的工作而忙碌。
> 
> **改为围绕价值组织团队——减少团队数量**
> 
> - 平衡团队覆盖范围和目标范围。
> - 小团队可以并且应该围绕目标组织（跨产品/技术）。
>     - **示例**：TransferWise：保留率、新货币、用户获取。
>     - **理由**：可以让团队拥有目标的所有权，并通过成果来衡量成功。
>     - **理由**：较少的团队有助于优先排序——没有无用的工作。
> 
> **价值流定义**：所有为客户传递价值所需的活动。
> 
> - 发现问题 → 设定目标 → 设想日期 → 交付产品或服务
> - 围绕价值流组织团队。优化流程以更快地将价值推向市场。
> - 从你为用户提供的价值开始倒推。思考客户的接触点：
>     - 如何通过客户旅程更快地提供更多价值？
> 
> **不要被产品混淆**。产品是价值的载体。如果某些东西本身不增加价值，它只是更大产品的一部分。超越应用程序、功能和界面，来构建你的团队。
> 
> - **例如**：汽车保险有一个应用程序，但没有汽车保险本身，应用程序毫无价值。
> - **你的产品经理应是汽车保险部门的一部分（而不仅仅是应用程序团队）**。围绕价值流组织的示例。
> 
> **保持战略与价值执行的统一。**

# 产品战略（Product Strategy）

- 战略是关于方向和决策制定的，关注结果（目标和愿景）
    - **战略 ≠ 计划**。战略应超越迭代和功能。
    - 在没有验证的情况下锁定一个计划，你可能会冒着构建客户不需要的产品的风险。
    - 战略可以在组织的不同层次创建。
    - 一个好的战略可以支持一个组织多年——如果不断变化，那只是一个计划，而不是战略。

**战略是一种可实施的决策框架，能够在当前能力的限制下，协作一致地实现期望结果。**

*——Stephen Bungay，《行动的艺术》*

Netflix 示例

- 作为一家DVD业务公司，他们开始将收入的2%投资于流媒体业务。
- **愿景**：以最方便和简单的方式为客户提供电影和电视节目。
    1. 在DVD业务上做大
    2. 领导流媒体市场
    3. 全球扩展
- 放弃了他们的硬件设备，并将Roku分拆出去。因为如果他们拥有自己的硬件，关键合作伙伴可能会将其视为威胁。
- **愿景演变**：
*“成为全球最佳娱乐分发服务，通过向世界各地授权娱乐内容，创造易于电影制作者获取的市场，并帮助内容创作者找到全球观众。”*
- Netflix 围绕关键结果和战略组织起来，以帮助实现其目标：
    - 个性化、即时访问、易于使用。团队能够探索策略来实现这些目标，并对每个目标的成功指标负责。
    - **以难以复制的方式取悦客户，同时增强利润率。**

战略与战术的示例对比

| **战略** | **战术** | **衡量指标** |
| --- | --- | --- |
| **个性化** | 评级系统、Netflix 奖 | 6周内评分超过50部标题的客户比例 |
| **即时** | 扩展中心、流媒体服务 | 一天内交付的光盘比例，或每月观看超过15分钟的客户比例 |
| **提升利润率** | 历史观看记录、广告、价格和计划测试 | 毛利率、LTV（生命周期价值） |
| **简单** | 简化并取消渐进式披露 | 第一天有超过3部影片在队列中的客户比例 |

**战略框架**（如Netflix使用的框架）迫使你在深入细节之前先关注整体。

**它提供了放大视角的能力（IT PROVIDES THE ZOOM OUT）。**

### 当战略出现问题时——差距（Gaps）

企业经常未能实现预期目标。失败通常来自于结果、计划和行动之间的以下差距。

### 知识差距（Knowledge Gap）：

*管理层想知道的 ≠ 公司实际知道的*

- 只要求足够的信息来帮助你做决策。
- 管理层应定义战略意图或业务目标，指向业务期望实现的结果。

### 对齐差距（Alignment Gap）：

*人们做的 ≠ 管理层想让他们做的*

- 更详细的指令无济于事。
- 应允许公司内的每一层级定义如何实现更高层级的意图。
- 确保团队的活动与公司目标的结果相连接。
- 不要下达命令，相反——对齐每一层级的“为什么”，并让下一层级决定该做什么并报告反馈。
- **领导层缺乏对齐往往会阻碍成功的产品管理。**

### 效果差距（Effects Gap）：

*我们期望行动达到的 ≠ 实际发生的*

- 当没有得到预期结果时，不要增加更多控制措施。给予团队更多自由，以调整他们的行动以实现目标。

### 自主团队（Autonomous Teams）

- 如果没有自主性，产品经理会感到沮丧。
- 产品经理经常被要求拥有产品的愿景——但他们却没有被允许，而是被交付解决方案。
- 产品经理认为领导层描述得过于详细，而领导层则认为产品经理没有承担起愿景的责任。
- **自主性是使组织能够扩展的关键。**
- 如果你对齐一致，并拥有一个良好的战略框架，你可以允许人们在不需要大量管理的情况下做出决策。

---

### 创建一个良好的战略框架

- **领导层是否对齐？**
- **产品经理是否知道他们为什么要做这些事情？它是否服务于战略目标？**
- **OKRs（目标与关键结果）有帮助。确保它们是结果导向的思维，而不是行动导向的思维。**
- **战略的两个部分**：
    1. **操作框架** - 保持日常运行。
    2. **战略框架** - 通过迭代产品和服务，在市场中实现愿景。
        - 战略和愿景 → 与 → 产品团队对齐。
        - 避免计划和执行的混乱（不要每年一次，而是持续评估）。
        - *Spotify 示例*：
            - 数据+洞察+信念 → 构成下注（DIBBs: Data + Insight + Beliefs → Inform Bets）。
            - 不要下达命令 → 提供一个可以尝试新事物并失败的环境。
- 当产品团队和管理层同步时，战略在发挥作用，并且结果数据被反馈到流程中。

### 战略的部署（Strategy Deployment）

战略是贯穿整个组织的相互关联的故事，解释目标和结果，并针对特定的时间框架量身定制。我们将这种传递和对齐的过程称为“战略部署”。

- 不同层级以不同的时间跨度讲述故事。
    - 敏捷团队思考2-4周后的事情。
    - 高管思考5年后的事情。
- 战略部署是在整个组织中设定目标和任务。团队需要适当水平的方向（既不过于狭隘，也不过于宽泛）。OKRs是一种战略开发方式。

战略的四个层级

| **层级** | **问题** | **责任人** |
| --- | --- | --- |
| **愿景**（公司） | 我们希望在5-10年内成为什么？为客户创造的价值、市场定位、业务的样貌。 | CEO / 高级领导层 |
| **战略意图**（公司） | 实现愿景的过程中存在哪些业务挑战？ | 高级领导层 / 业务负责人 |
| **产品目标**（产品） | 我们可以从产品角度解决哪些问题以应对这些挑战？ | 产品领导团队 |
| **选项**（产品） | 我有哪些不同的方法可以解决这些问题以实现我的目标？ | 产品开发团队 |

---

### 战略的创建（Strategy Creation）

- 战略需要识别问题，并组织团队（在不同的层级）围绕解决这些问题展开工作。
- 不要指望一天之内就能创建一个战略。
- 将战略付诸实践：定义愿景 → 识别问题和障碍 → 试验。然后重复，直到实现愿景（持续改进）。

**这就是产品Kata方法（Product Kata）**。

**步骤1、2、3是战略的创建和开发。步骤4是执行。**

### 产品Kata的步骤

1. **理解方向**
    - 公司愿景和战略意图
    - 产品目标
2. **分析当前状态**
    - 意图的当前状态
    - 目标/产品的当前状态
3. **设定下一个目标**
    - 产品目标
    - 选项目标
4. **选择产品流程的步骤**
    - 问题探索
    - 解决方案探索
    - 解决方案优化

**选项目标**是你需要实现的结果，以便在你的目标或意图上取得进展。在探索和识别问题时，你会发现数据，它可以为战略和愿景提供信息。

## 公司层级的愿景和战略意图

### 公司愿景

愿景为接下来的所有内容设定方向并赋予意义。它是战略的基石，应该保持稳定。

> “成为地球上最以客户为中心的公司，让顾客能够在线找到并发现他们可能想购买的任何商品，并努力以最低的价格为顾客提供服务。”
> ——Amazon的愿景声明

战略需要从公司层级开始，并贯穿到业务线。如果愿景声明不清晰，需要重新定义。

**战略意图帮助将愿景与公司运营连接起来——这是战略中最困难的部分。**

---

### 战略意图

战略意图是用于传达重点领域的工具。它们是以结果为导向的宏大目标，通常需要1-5年的时间来完成。

- 限制意图数量至少数几个——目标是创建专注于如何实现愿景的框架。
- 由于战略意图与公司的当前状态对齐，因此它们可以随时间改变。

### 战略意图需要回答的问题：

5. 根据我们目前的状态，为了实现我们的愿景，我们可以做的最重要的事情是什么？
6. 为了向愿景迈出一大步，需要发生的少数几件事情是什么？

---

### 示例：意图 → 目标

| **意图** | **目标** |
| --- | --- |
| **扩展企业业务** | 在3年内将收入从500万美元增加到6000万美元 |
| **个人用户收入翻倍增长** | 将个人用户收入同比增长从15%提升到30% |

**注意**：

- 意图过多会导致分散注意力（如“涂抹花生酱”般均匀分散）。限制为3个意图。
- 保持高层次和业务聚焦，专注于整个公司，而不仅仅是产品解决方案。

---

## 产品愿景与产品组合

### 产品愿景

产品愿景将功能和交付价值的方式与客户联系起来。它传达了为什么要构建某些东西以及这些东西对客户的价值。

- **产品愿景的核心**：通过解决用户问题而产生。它应该经过验证。
- **产品愿景声明**：
    - 包括用户面临的问题以及产品将提供的能力。
    - 不应包含功能。
    - 可以包含对用户重要的品质（如易用性）。

通常由产品副总裁（VP of Product）负责产品愿景，但他们可能不是最早设定愿景的人。

---

### 产品组合

为了设定产品组合的方向，回答以下问题：

7. 我们所有的产品如何作为一个系统协同工作，为客户提供价值？
8. 每条产品线提供了哪些独特价值，使其成为一个引人注目的系统？
9. 在决定新产品解决方案时，我们应该考虑哪些整体价值和指导原则？
10. 我们应该停止做什么或停止构建什么，因为它不符合这一愿景？

**产品组合战略**通常由首席产品官（CPO）负责。领导者需要腾出时间进行创新。

# 产品管理流程（The Product Management Process）

最好的解决方案与用户想要解决的真实问题相关联。产品经理使用流程识别可以解决的问题，并推动战略的实现。

产品经理可以依靠**产品Kata**（Product Kata）来培养正确的实验思维方式，专注于问题本身（而非解决方案）。你可以不断迭代，直到达到期望的结果。

---

### **构建陷阱警告**

> 当你更关注构建软件，而非构建正确的软件时，就会陷入构建陷阱。
> 通过理解和运用解决问题与实验技术，你可以避免陷阱，从而实现最重要的事情。

---

### 产品Kata（Product Kata）

通过这个流程，我们可以发现正确的解决方案来构建产品。这是一种从解决问题的角度出发进行产品构建的方法。

产品经理和团队应该按照以下步骤逐步推进，发现产品目标和可选方案。

11. **理解方向**
    - 公司愿景和战略意图
    - 产品目标
12. **分析当前状态**
    - 当前意图状态
    - 当前目标/产品状态
13. **设定下一个目标**
    - 产品目标
    - 可选目标
14. **选择产品流程步骤**
    - 问题探索
    - 解决方案探索
    - 解决方案优化

---

### 阶段1：明确产品目标

从理解战略意图及评估当前状态开始，确定你的产品在实现战略意图中的作用。

- 识别你可以通过产品解决的问题，这可能会出现许多选项。
- **为了判断是否接近实现产品目标，你需要将成功指标分解为可以在短期内衡量的内容。**
    - 这成为团队的目标——即如何衡量可选方案的成功。
    - 改变一个产品目标可能需要6个月或更长时间，但团队目标必须在每次发布后可衡量。
    - 这样可以为团队提供反馈，并让他们知道某个选项是否有效。

---

背景重要性（Context Matters）

在设定目标后，我们开始执行产品Kata流程：

15. 目标是什么？
16. 当前状态与目标的关系如何？
17. 实现目标的最大障碍或问题是什么？
18. 我将如何尝试解决这个问题？
19. 我期望发生什么？（假设）
20. 实际发生了什么？我们学到了什么？

---

常见错误（Common Mistakes）

- 在错误的阶段应用工具或实践，例如：在已有明确解决方案时进行不必要的实验。
- 为非核心价值主张的事情过度设计解决方案（如登录）。如果问题在其他地方已解决，复制并验证即可。
- 专注于那些可能对你的价值主张造成重要影响的事情。

---

原则（Principles）

- 所有设计和开发工作都应服务于实现目标。
- 不一定需要发布任何东西——鼓励停止坏的想法。
- 功能越少越好。
- 专注于质量而非数量。

---

指标（Metrics）

设定成功指标。这样可以帮助你理解方向并衡量进展。确保使用正确的指标：

- **产品指标（Product Metrics）**
    - 帮助你识别需要采取行动的地方，通过展示产品和业务的健康状况影响产品方向。
- **虚荣指标（Vanity Metrics）**
    - 对产品团队的决策帮助不大，也无法改变行为或优先级。可以通过添加时间组件让其更具可操作性。
- **生产力指标（Productivity Metrics）**
    - 如燃尽图、用户故事、已发布功能。这些不是产品指标，而是将产品开发结果与战略连接起来。

---

两种指标框架（Two Metric Frameworks）

**海盗指标 - AARRR（Dave McClure）**

| **阶段** | **描述** |
| --- | --- |
| **获取** | 用户找到你（注册和登录） |
| **激活** | 用户的首次体验（采取了有意义的步骤） |
| **留存** | 保持用户的持续回访 |
| **推荐** | 用户因喜欢你的产品而推荐他人 |
| **收入** | 用户为你的产品付费 |

**HEART框架**

| **阶段** | **描述** |
| --- | --- |
| **幸福感** | 用户的满意度 |
| **参与度** | 用户与产品互动的频率 |
| **采用率** | 用户接受新功能的程度 |
| **留存** | 用户的持续使用情况 |
| **任务成功率** | 可用性测试——产品的易用性 |

**注意**：

- 仔细考虑指标背后的意义和背景。它们如何影响你的决策和理解？
- 例如：这个月你的活跃用户是否增加？如果是，你做了哪些不同的事情？

---

### 阶段2：问题探索（Problem Exploration）

- 数据分析可以告诉你发生了什么，但这并不是全部。
- 为了充分理解问题，你需要理解客户。
- 产品经理常常与客户沟通不足。
- **问自己**：
    - 实现目标的最大障碍是什么？
    - 接下来你需要学习什么？

---

平衡分析方法与以下方法：

| **方法** | **示例** |
| --- | --- |
| **用户研究** | 观察、调查、客户反馈 → 从用户角度理解问题 |
| **评估研究** | 可用性测试 → 它有效吗？ |
| **生成研究** | 观察性研究 → 帮助你识别问题： |
|   | - 最大的问题是什么？ |
|   | - 痛点是什么？ |
|   | - 问题的根本原因是什么？ |
|   | - 他们在解决方案中看重什么？ |

---

原则

- 不要问客户要构建什么，而是问正确的问题来理解他们的需求和期望。
- 在理解问题（及其根本原因）之前，不要开始解决问题。
- 在尽可能早的阶段测试假设（研究和实验在构建之前）。
- 尽早理解问题的工作可以节省时间——你将追逐正确的目标。

### 阶段3：解决方案探索

**通过实验学习（Experiment to Learn）**

在不确定性存在时，花时间在构建之前进行理解和实验是关键。

不要将“通过构建来学习”和“为了盈利而构建”混为一谈。

- 实验的目的是通过构建来学习——理解客户并验证解决问题的价值。
- 实验不应该设计为长期存在的——你想要尽快验证对错。
- 计划在必要时放弃你构建的东西，并找出如何使其可持续和可扩展的方法。

不要将**“最小可行产品（MVP）”**方法作为借口，专注于快速发布功能。

削减开发角度牺牲了学习机会。

- 将MVP视为最小学习努力的实现方法——它让你专注于结果，而非单纯的输出。

使用“**解决方案实验（Solution Experimentation）**”代替MVP。

实验的设计是为了帮助公司更快地学习（它们不是关于健壮性或可扩展性的）。

我们进行实验是因为在开始工作时，我们并不知道最佳的解决方案。

---

**产品Kata让你专注于学习**

问自己：“接下来需要学习什么？”

→ 保持团队方向一致，设置正确的实验。

**基本实验类型**

| **实验类型** | **示例** |
| --- | --- |
| **用户研究** | 观察、调查、客户反馈 → 帮助你从用户角度理解问题 |
| **评估研究** | 可用性测试 → 它是否有效？ |
| **生成研究** | 观察性研究 → 帮助你识别问题： |
|   | - 最大的问题是什么？ |
|   | - 痛点是什么？ |
|   | - 问题的根本原因是什么？ |
|   | - 他们在解决方案中看重什么？ |

---

**减少客户暴露**：

- 思考如何结束实验以关闭循环。
- Concierge、Wizard of Oz和概念测试都适用于高不确定性的问题。
- 原型不适用于验证问题，而是适用于探索解决方案。

**在复杂行业中进行实验**：

- 学习可以降低风险——发挥创造力。
- 如果不能在理想环境中学习，就要创新学习方法。
- 构建错误产品的机会成本太高——找到应对未知的方法至关重要。

---

### 阶段4：构建与优化解决方案

| **轮次** | **当前状态** | **需要学习的内容** | **下一步** | **预期** | **学到的内容** |
| --- | --- | --- | --- | --- | --- |
| **1** | 核心指标未发生变化 | 用户有哪些问题 | 用户研究20位客户 | 找出最大的问题 | 问题列表：A、B、C |
| **2** | 核心指标未发生变化 | 问题A的主要痛点 | 观察20位用户 | 识别关键问题 | 发现关键问题 |
| **3** | 核心指标未发生变化 | 大多数用户是否有此问题？ | 调查1000名用户 | 大多数用户有此问题 | 80%用户报告存在该问题 |
| **4** | 核心指标未发生变化 | 移除此步骤是否能改进指标？ | Concierge实验以移除此步骤 | 核心指标有所改进 | 核心指标对实验参与者有所提高 |

---

产品愿景的方向设定

确保每个人都理解背景和需要完成的工作。以下是两种方法：

---

**北极星文件（North Star Document）**

- 以团队和公司可视化的方式解释产品，内容包括：
    - 你正在解决的问题
    - 提议的解决方案
    - 解决方案成功的关键因素
    - 产品将实现的结果

**特点**：

- 为广泛的受众提供背景信息。
- 持续更新并根据学习调整演变。
- 不是行动计划，也不包括团队构建产品的详细信息。
→ 这一部分由故事映射（Story Mapping）来完成。

---

**故事映射（Story Mapping - Jeff Patton）**

- 分解工作并围绕目标对团队进行对齐。
- 帮助团队沟通和理解需要完成的工作。
- 从用户角度分解期望的操作。
- 在团队中建立共同理解。

---

优先级框架（Prioritisation Frameworks）

**（收益映射 - 延迟成本 - KANO模型）**

- 延迟成本可以量化，帮助优先工作：
    - **紧迫性**：每拖延一刻未发布功能，你就失去了客户或收入。
    - **价值**：解决客户最强烈的问题或需求。

---

改变你对“完成”的定义！

传统上，“完成”的定义是关键活动的清单——定义某物已准备好发布。

但如果只有在实现了业务和用户的预期结果时，才能真正称之为“完成”？

**→ 这是整本书中最重要的一点！**

---

成功或退出标准

- 在发布前设定成功或退出标准，同时测量并迭代，直到达到目标。
- 版本1应该是一个假设。
- **成功标准可用于产品Kata**：重复步骤，直到达到目标：
    - 以成功标准设定方向。
    - 了解实现目标的障碍是什么。
    - 系统性地通过实验解决问题。

无论是构建新功能，还是优化现有功能，过程都是相同的：

- 对于小型功能，问题探索可能很小。

==**这是如何有意构建，从而摆脱构建陷阱的方法。**==

# 第五部分：以产品为导向的组织

**以产品为导向的组织**的特点是拥有一种理解并**围绕结果而非输出进行组织**的文化。

- 战略围绕实现结果（而非输出）进行组织和调整。
- 员工因学习和实现目标（而非仅仅完成发布）而获得奖励。
- 鼓励团队与客户建立紧密联系。
- 产品经理被视为推动业务发展的关键职能。

---

## **以市场为驱动的创新**

通过生成性研究深刻理解用户的行为模式、关注点和需求，将自己沉浸在用户的问题之中。

### **Kodak案例：接近成功的创新**

- Kodak在早期数字摄影阶段进行了生成性研究：
    - 用户希望能够控制自己展示的方式。
    - 用户希望在发布照片前编辑它们以获得更好的效果。
    - 用户希望手机摄像头功能更强大。
- *“你应该考虑如何将相机技术集成到手机中。”* 也许是手机上的照片编辑软件，以及分享照片的功能。
- **选项**：
    - A - 自主生产手机。
    - B - 向手机制造商提供技术支持。
- **Kodak尝试进行创新，但组织架构阻碍了其前进**：
    - 创新实验室的小团队无法改变企业的未来。
    - Kodak在6个月内无法获得预算支持。

**要摆脱构建陷阱，你需要成为一家以产品为导向的组织。**

这需要在思维方式和实践上进行改变，同时调整沟通方式、文化、政策和奖励机制。

---

## **以结果为导向的沟通**

- 你需要理解结果——并了解“看到结果”的意义。
- **注意**：
> 当企业缺乏足够的耐心等待结果显现时，会陷入构建陷阱。他们转而通过发布功能的数量来衡量进展。

### **如何变得更加耐心**：

- 开会审查进展。
- 让公司活动和结果变得透明化。
- 针对不同层级的受众，调整沟通节奏和内容。

### **阻碍企业转型为以产品为导向的主要原因是领导层缺乏支持**：

- 输出让人感觉良好，人们觉得自己实现了目标——只是完成了任务清单。
- **我们必须记住：发布产品并不是衡量成功的唯一标准。**

---

## 可见性至关重要

领导者越能清楚地看到团队所处的位置，他们就越愿意放手并让团队执行。透明化可以让你更自由地实现自治。

**采用一个与战略框架（愿景、战略意图、产品目标、选项）相匹配的沟通方式。**

---

**示例：沟通结构**

| **会议类型** | **频率** | **内容** |
| --- | --- | --- |
| **业务审查** | 季度（高级领导层） | 分享战略意图的进展。共享财务和结果指标（收入、流失率、运营成本）。CPO和产品副总裁说明产品目标如何推动战略意图。可以引入新的战略意图。**避免优先考虑产品目标。** |
| **产品目标审查** | 季度（产品与设计领导者） | 审查选项相对于产品目标的进展。实验、研究、发布的结果及其与目标的关系。讨论新的产品目标、反馈、支持需求。资金请求。 |
| **发布审查** | 每月 | 团队展示他们的努力工作。讨论成功指标。关注即将发布的内容。与销售、市场和高管沟通路线图。**不要讨论实验或未发布的事项。** |

---

### 路线图与销售团队

- **展示包含功能和日期的路线图可能导致过度承诺和未能交付的恶性循环。**
- **将路线图视为对战略和产品当前阶段的解释（而非计划）。**

### **建议：**

- 将战略目标与主题和产品交付结合起来。
- 保持路线图的动态性——不断更新。
- 针对不同的受众调整路线图。

**可以包含**：主题、假设、目标和成功指标、状态、里程碑等。

**建立一个共享的术语体系来描述开发阶段（Alpha、Beta等）**。

| **开发阶段** | **说明** |
| --- | --- |
| **实验阶段** | 理解问题并确定是否值得解决。进行问题探索和解决方案探索活动。 |
| **Alpha阶段** | 解决方案是否符合用户需求？最小功能集或健壮的实验。早期访问——功能可能会被取消。 |
| **Beta阶段** | 确定解决方案是否具有可扩展性。降低风险。仅向一小部分用户开放。 |
| **全面可用阶段** | 面向所有客户开放。 |

### 大型组织的产品运营团队

大型组织可以从**产品运营团队**中获益：

- **职责**：
    - 跟踪进展、目标，并集中管理流程。
    - 通常由直属于CPO的幕僚长或副总裁领导。

职能：

- 设置战略节奏。
- 报告目标、结果和进展。
- 有时会创建产品分析平台并提供指标支持。
- 标准化产品流程。
- 组织关键产品会议。
- 为产品团队提供指导或培训。
- **不创建路线图**，而是创建一个系统和模板，使团队能够输入目标、主题、进展和细节，并在组织中共享。

---

### 奖励与激励

- **评估现有的奖励结构以激励正确的行为**。
    - **不要将薪酬与发布挂钩。**
    - 避免“只要发布这个功能就可以”的思维。
    - 不要因公司政策而将员工推入“构建陷阱”。

**奖励重点**：

- 对实现结果、了解用户以及发现商业机会的人给予奖励。
- 我们希望营造一个实验和学习的文化。

**赋能团队**：

- 鼓励团队与上级沟通，讨论成功的真正含义。
    - 定义你的指标 → 始终带上数据。
- 避免销售过度承诺（例如，佣金比重过高的奖励结构）。

---

### 安全与学习

- **在公司中建立安全感，让产品经理能够实验、失败和学习。**
- **庆祝学习，而非失败。**
- **领导者需要设置边界**：边界使实验文化更少令人害怕。
    - 边界可以是时间、预算或用户群体。

**产品经理的关键作用**：

- *“最昂贵的错误是构建一个不确定是否为正确产品的产品。”*
- **问题**：如何测试并确保这真的是我们想要的？

---

### 预算管理

- **年度路线图与预算绑定**：将未来几年的资金与承诺的交付挂钩，可能导致“为保留资金而构建”的文化。
- **新策略**：像风险投资一样资助产品：
    - 将资金分配给已知的产品线（准备好构建或维护）。
    - 将资金分配给推动商业模式前进的新机会。
    - **并非所有投资都从小规模开始**——用数据和证据支持更大的投资。

---

### 以客户为中心

- **创建以客户为中心的文化**：
    - 高管如何对待客户至关重要。
    - 站在客户的角度思考：
        - “什么能让你的客户满意并推动业务前进？”
        - “最重要的事情是深刻理解你的客户。”

# 结论

摆脱构建陷阱需要整个组织的变革：

- 专注于结果，而非输出。
- 确保合适的人处于合适的位置。
- 建立良好的战略或部署流程。
- 确保拥有正确的结构和政策。

---

### 判断你是否以产品为导向的问题

**1. 你最近构建的功能或产品创意来自谁？**

- 应该来自团队，而不是管理层。
- 管理层设定目标——给予团队空间去探索如何实现目标。

**2. 你最近决定终止的产品是什么？**

- 如果无法终止不符合目标的产品或想法，这是一种不健康的状态。
- 是否提前向客户承诺了这些产品？
- 预算是否僵化？
- 管理层是否允许反对意见？

**3. 你上一次与客户交流是什么时候？**

- 管理层是否限制了这种交流？

**4. 你的目标是什么？**

- 产品经理应该能够清晰表达目标：
    - 应该是结果导向的、可执行的、清晰传达的。
    - **不应是输出导向的！**
- 通过为客户创造价值来为业务创造价值。

**5. 你目前在处理什么工作？**

- 为用户和业务解决问题（而非仅提供解决方案）。
- 仅在解决问题的背景下讨论解决方案。

**6. 你的产品经理是什么样的？**

- 产品经理应该受到尊重，被视为引领公司方向的领导者。
- 产品经理不应显得过强或过弱：
    - 不是独裁者，但也不应被利益相关者或管理层压制。


**7. 你是否对最近发布的内容进行了迭代？**
