# 前言

- 我们的目标是为富有挑战性的问题构建有影响力的解决方案，但多数情况下，我们未能实现预期的结果。
- 产品方向的意义在于：
    - 选择需要解决的正确问题
    - 将问题分解为可执行的机会和可衡量的目标
- 产品方向是一种实用的方式，用于定义、链接和传达你的产品战略、战略路线图和目标，以帮助对齐、聚焦并扩展你的产品组织的影响力
    - 利用OKR方法
- 人员和团队对模糊的愿景可能会有不同的解读，导致出现不一致的情况，你无法实现期望的影响力。
- 为什么要改变？
*推动力*
    - 平庸的影响
    - 努力浪费在错误的问题上
    - 团队未能一致对齐
- 为什么我们没有改变？
*阻碍力*
    - 缺少框架/方法
    - 职责不明确（解决问题是谁的工作？）
    - 短视（专注于下一次发布）
    - 长反馈周期
- 方法的优势：
    - **团队对齐和自主性**。所有团队专注于通过正确的路径实现愿景
    - **聚焦和定位**。选择并承诺提供最佳结果的机会，同时拒绝其他机会
    - **规模化和一致性**。自主性和对齐性使你能够在保持速度和成功的同时实现规模化
        - 共享的实践、工具、文物、沟通方式和透明性

# 第一部分：制定产品战略

## 第1.1章：战略简介

- 产品战略是愿景与预期成果之间的桥梁。
- 产品战略包括：
    - 对当前情况的诊断
    - 你正在关注的一部分机会/问题
    - 执行的指导方针
- 为什么组织在产品战略上失败：
    - 缺少方法
    - 缺乏问责机制
    - 缺乏洞察产生
    - 方向的不断变更
    - 缺乏承诺/专注
    - 沟通不畅
    - 在错误的细节层次上制定战略
- 在正确的层次上制定产品战略：
    - 层次过高 → 销售额增加20%
        - 没有具体的方向
        - 没有关于如何实现的指导
    - 层次过低 → 为一年制定50个战略项目
        - 过于限制，可能是以产出为导向而非成果为导向
    - **你的战略应描述实现产品愿景的路径**
- 愿景模板：
    1. 你的愿景应描述通过神奇地解决困难且持久的问题，在未来3-5年内产品将带来的积极且以客户为中心的变化
    2. 针对（目标客户）需要（需要陈述），（产品名称）是一种（产品类别），具有（关键利益陈述/购买的令人信服的理由）。与（主要竞争对手替代方案）不同，（产品/品牌名称）提供了（主要差异化陈述）。
- 你的产品战略应与公司的愿景、抱负和战略对齐，从而帮助公司实现它们
    - 示例：YouTube的多年度雄心：到2016年每天观看时间达到10亿小时
- 根据一个公司的发展阶段，目标可能会有所不同：
    - 初创阶段：快速增长、用户获取和激活
    - 成长期：利润率、盈利能力
    - 成熟期：扩展到新细分市场、地理区域、类别
- 产品战略应直接聚焦于一组机会和活动，这些活动将支持公司实现抱负

## 第1.2章：战略创建过程

- 你需要生成并消化大量洞察以确定正确的方向：
    - 定义：先前决定的内容
    - 结果：使用和性能数据
    - 外部：其他地方发生了什么？竞争、新趋势等

| 定义 | 结果 | 外部 |
| --- | --- | --- |
| 公司：愿景和使命 | 公司KPI | 行业报告 |
| 客户：细分和需求 | 客户反馈 | 客户研究 |
| 产品：产品愿景 | 产品KPI，技术状态 | 基准比较 |

- 九个需要了解的事项：
    1. 愿景和使命声明 → 知道目标方向
    2. 客户细分、用户角色和需求 → 知道服务对象
    3. 公司结果 → KPI，生命周期阶段
    4. 产品结果 → AAARR指标，行为分析
    5. 客户反馈 → 客户满意度、客户服务洞察、社交媒体提及，与产品性能相关联
    6. 客户研究 → 定性研究揭示原因、发现未满足需求
    7. 市场和行业分析 → 了解市场环境、市场增长、竞争、趋势和数据
    8. 基准比较 → 竞争对手的结果和表现。如何与行业最佳进行比较？不仅比较竞争对手，还比较替代方案、不同行业和颠覆者
    9. 技术状态 → 技术债务、扩展能力、性能、所需投资
- 需要参与的人：
    - **你需要在战略思维与产品计划的详细知识和结果之间找到平衡**
        - 产品领导力 + CTO + 技术领导力 + 产品经理
        - **在获取所有洞察与参与过多人员之间存在权衡**
        - 需要有人对计划负责，拥有权威并做出最终决策（CEO、CPO或产品副总裁）
    - **两种战略层级：**
        - 组合层级：
            - 高层，高级人员。识别关键关注领域（问题/机会）并分配资源。
            - 确定团队可以对齐以产生影响的方向。
        - 产品层级：
            - 产品团队将主题与组合对齐。包括团队成员（而非经理）。
            - 从发现、基准比较或实验中识别机会。
            - 即使将组合和产品层级分开，每个层级的决策都会影响另一层级。
- 利益相关者应参与战略共创：
    - 将他们纳入循环
    - 获取他们的宝贵洞察和反馈
    - 通过让他们参与保持动力
    - **但50人辩论 → 瘫痪，通过妥协和集体思维达成共识 → 阻碍突破**
        - 提前获得想法和洞察 → 事后进行沟通和反馈
    - 有人负责组合战略是有益的 → 产品经理应对产品战略负责
- 节奏：
    - 根据你的行业，12到18个月的产品战略是合适的。
    - 持续审查以纳入新学习和发现。
    - 意外结果可能需要调整方向。
- 战略创建过程：
    - 收集信息
    - 整合洞察
    - 选择
    - 目标
    - 综合
    - 传达

### 第0步：收集信息

- 收集与产品战略相关的数据应该是一个持续的努力：
    - 用户、商业、市场、竞争对手、宏观经济条件等
- 战略定义应从关键信息的总结开始
- 需要划分输入...明确指出每个信息由谁提供

| 产品层级 | 公司层级 |
| --- | --- |
| 公司结果：产品负责人 | 公司结果：CPO |
| 客户研究结果：产品设计师 | 客户研究结果：UX部门负责人 |
| 客户反馈：产品设计师 | 客户反馈：UX部门负责人 |
| 产品行为结果：产品经理 | 产品行为结果：产品负责人 |
| 基准比较：产品经理 | 基准比较：产品负责人 |
| 产品技术状态：技术负责人 | 产品技术状态：CTO |
| 行业报告：所有人 | 行业报告：所有人 |

- 利用利益相关者和合作伙伴的宝贵信息或基准比较
- 数据应经过筛选、提炼并以易于他人理解其重要性的方式呈现

### 第1步：洞察

- 从这些信息中，**你需要选择正确的洞察来专注**。
- 生成尽可能多的洞察 → 以便稍后选择最有前景的机会。
- 但我们只寻找能够改变局面的**问题、趋势或机会**。
- **洞察是具有高潜力影响用户需求和业务结果的学习成果**。
- 你已经拥有洞察 → 现在需要将它们整合并澄清。

### 洞察框架

- 内部 vs 外部

|   | 业务洞察 | 客户洞察 |
| --- | --- | --- |
| 外部 | **外部业务洞察**<br>业务模式变更<br>例如：低成本航空 | **外部客户洞察**<br>消费者行为<br>例如：流媒体服务 |
| 内部 | **内部业务洞察**<br>自动化（如何使用工具）<br>重新定位（作为企业的内部能力）<br>例如：Amazon AWS | **内部客户洞察**<br>产品行为<br>例如：Facebook > 7 位好友 |

- 创新来源（Peter Drucker）
    - 内部来源：
        - 有没有发生任何意外情况？意外的成功或失败？这可能导致机会吗？
        - 客户仍然在产品中遇到哪些问题？
        - 还有哪些流程可以改进？
        - 行业或市场中是否有重大变化？（干扰或趋势）
    - 外部来源：
        - 我们的客户是否在发生变化？或者细分市场的规模是否变化？
        - 人们的看法是否发生变化？是否可以利用？
        - 技术或其他领域是否有突破可以实施？
- 创新的10种类型（Larry Keeley）
    - 三个机会领域：
        - 业务模式和运营的配置
        - 产品提供的价值
        - 客户从公司获得的体验

洞察工具

- 列出你的洞察 → 产生有影响力的想法
- 激发创造力并引入你不常考虑的选项
- 专注于先前的洞察

- **将你的产品与竞争对手进行基准比较 → 确定你的核心价值差异化**

### 第2步：选择

- 专注于极少数具有决定意义的目标 → 如果实现，将带来一系列有利结果。
- 聚焦于最有前景的战略驱动因素 → 确保理解追求它们所需的必要取舍。
- 过程：
    1. 决定哪些洞察将对结果产生最大影响。
    2. 理解它们如何相互作用。
    3. 将选择与可用资源对齐。
- 选择的核心是聚焦和定位：
    - **使整个组织与希望在客户价值主张中实现的差异化对齐**。
        - → 基于已识别的洞察和机会。
    - 这不仅仅是优先排序 → 你需要理解目标及每条路径的假设/风险。
- 考虑与目标的一致性：
    - 理想情况下，你的洞察/路径与目标对齐，你可以选择最佳路径。
    - 但：
        - 你可能没有明确的目标可对齐。
        - 你可能会发现与目标冲突的机会。（例如：你没有计划进入新国家，但你从那里获得了客户询问。）
        - 如果是这样，请将问题提交给CEO和其他利益相关者。
- 赢得选择：
    - **选择制胜策略 → 确定制胜战略，否则你将无法做出资源投资和承诺，成为细分市场的领导者**。
    - **选择一个使你能够主导利基市场或基于客户高度评价的关键属性进行竞争的战略**。

选择工具

- 当前战略显然是一个有用的考虑因素。
- 早先已识别的洞察工具同样重要。

工具1：强化核心

- 最有用的工具之一：
    - 选择并分组那些增强当前核心业务和价值主张的洞察。
    - 苹果的服务生态系统强化了其核心设备业务，并帮助所有设备更好地协同工作。
    - **利用动态 → 利用优势地位 → 战略优势难以获得 → 一旦拥有，强化你的地位，并深入明确差异化，从而充分发挥其潜力**。
- 在白板中央写下你的产品提供：
    - 将最有价值的洞察放在中央周围。
        - 连接你的洞察与产品 → 说明该洞察如何改善核心产品。
        - 连接你的产品与洞察 → 说明你的核心价值如何使该机会更具吸引力且更有可能实现。
        - 然后删除孤立洞察 → 即无法连接到产品的洞察。
        - 接着根据期望结果做出选择。

工具2：谷歌的70/20/10规则

- 70%的资源用于核心业务。
- 20%用于新兴机会。
- 10%用于新投资 → 高风险，高潜在回报。

工具3：吉布森的DHM框架

- 吉布森·比德尔的定义：产品领导者应该做的是：
    - **取悦客户**。
    - **增强利润**。
    - **以难以复制的方式**。
- 使用这个框架分析每个机会 → 根据三个标准评估每个洞察。

一致性过滤器

- 选择最有前景的想法进行解决。
- 你在寻找一个将公司与特定定位对齐的整体战略。
- 选定的选项是否兼容？
- **它们是否都指向相同的方向？**
    - 例如：不要同时尝试进入新市场和减少成本。
- 尽量避免不一致！如果无法避免，请清晰传达：
    - 例如：削减成本，但与新市场扩展相关的成本除外。
    - **战略中的这种例外情况会增加沟通和实施的难度**。

### 第3步：目标和假设

- 选择要关注的洞察需要事先设定预期结果。
- 为每个洞察定义成功的衡量标准也有助于选择。

| 机会类型 | 目标 | 假设 | 失败概率 | 影响 |
| --- | --- | --- | --- | --- |
| 洞察名称 | KPI及其期望值 | 达成结果需要满足的条件 | 失败的可能性 | 失败对结果的严重影响程度 |

- 如果你选择一个洞察，就需要承担假设可能出错的风险：
    - 在选择阶段记录关键假设。
    - 根据你已知的信息以及完成的探索量，信心会有所不同。
    - 外部洞察通常比内部洞察更脆弱。


评估假设

- 需要证明关键假设是正确的，以验证你的假设。
- 谨慎评估与每个假设相关的风险：
    - 根据“可能性 vs 影响”评分：
        - 分配1至5的分数，然后相乘。
        - 例如：可能性5 x 影响5 = 25。
    - 不确定性取决于证据的数量。


时间视角的考虑

- 第二和第三视角中的机会无法以相同方式量化。
- 不能将新兴机会与公司的核心收入来源进行比较。
    - 不要陷入“因缺乏早期结果而扼杀新兴机会”的陷阱。
    - 关注增长和留存率，而不仅仅是新业务的收入。
- **经验证的学习**（Eric Ries），构建-测量-学习。
- 目标是获得明确的确认或拒绝。

| 时间视角 | 目标类型 |
| --- | --- |
| 第一视角：核心业务 | 常规目标，北极星指标 |
| 第二视角：扩展 | 高增长和高留存 |
| 第三视角：押注 | 经验证的学习量，早期交易 |

高层资源理解

- 你的选择必须现实地反映你执行这些项目的能力：
    - 努力 = 资源、时间和范围。
- 在此阶段只有有限的精确性。

### 第4步：综合

- 综合涉及创建一个能使你的战略清晰且令人难忘的工件。
- 不要仅仅列出需要解决的问题清单。请考虑：
    - **原因** → 为什么解决它们至关重要？根本原因是什么？如果解决了，它会对客户和业务产生什么影响？
    - **讲故事** → 讲述一个故事，解释你的出发点、意图以及未来将如何。
    - **视觉化** → 使用视觉元素使战略看起来令人难忘。

综合工具

工具1：驱动因素模型

- 3到5个支柱/驱动因素显示在一个图像中。
- 元素：

完成战略文档：

- 试着描述你经历的过程。
- 你可以涵盖的内容：
1. 回顾公司和产品。
2. 诊断信息（指出关键信息和不同来源）。
3. 洞察和选择。
    - 引导他们了解你已识别的选项。
    - 说明“为什么”。阐明重要性。
    - 说明你不会做什么！
4. 得出的方向：
    - 用一个令人难忘的图像描述战略。
    - 作为沟通的核心内容。

    - KR或KPI。

战略沟通

- 要让战略成功，每个人都需要了解并理解它。
- **未知或未被理解的战略是无用的。**

---

- 思考如何最好地让利益相关者参与战略流程。
    - 你可以在洞察和选择阶段获得他们的帮助。
    - 如果没有关键成员的同意就承诺一个方向或目标，将影响沟通阶段。
- 两种不同的参与方式：
    - **共同创建和讨论**：帮助你更深入地理解并产生高度一致性。
    - **反馈提案**：在做出选择后，征求并开放接受反馈。
- 思考关键利益相关者的需求：
    - 理解他们的目标。
    - 理解他们当前的挑战或关注点。
    - 选择对他们意味着什么？
- 构建共同理解：
    - 在选择过程中，每个人需要共享相同的愿景，明确目标。
    - 用可视化的方式呈现。
    - 花时间确保每个人都在同一频道上。
- 达成共识：
    - 通过可靠数据说服。
    - 通过实验验证（如果有可以轻松验证的关键假设）。
- 沟通会话：
    - 在导航利益相关者之后，需要向全组织传达信息。
    - **潜在结构**：
        - 高层管理（在会话前考虑单独沟通，验证你的故事）。
        - 产品领导团队和完整的产品团队（深入讨论数据和潜在影响）。
        - 特定的产品利益相关者和群体（各类利益相关者/部门）。
- 寻找其他方法加强信息传递：
    - 在墙上张贴。
    - 将目标或行动中的驱动因素链接起来（目标 → 方向）。
    - 将日常工作与战略连接起来，鼓励人们持续关注战略。
- **重复信息** → 不要依赖单次会话。

战略评估的四个方面（来源：Rumlet文献）

| 方面 | 问题 | Rumlet观点 |
| --- | --- | --- |
| **一致性** | 战略是否与公司的愿景、需求和资源保持一致？ | **战略不得呈现出相互矛盾的目标和政策。** |
| **和谐性** | 是否考虑了客户和市场趋势？ | **战略必须对外部环境和其中发生的关键变化作出适应性反应。** |
| **可行性** | 是否可实现？是否考虑到了团队能力？ | **战略不得超过可用资源，也不得创建无法解决的次要问题。** |
| **优势** | 是否与定位一致？是否增强了竞争优势？ | **战略必须为创建和维护在特定活动领域的竞争优势提供条件。** |

第一个月 - 实验

- 开始运行实验以验证假设。
- 提供有用的学习以适应和改进方向。
- 找到验证问题和机会价值的测试类型：
    - 例如：问题访谈、原型测试。
        - 探索性访谈为战略创造洞察，但不会告诉你如何执行。
        - A/B测试或可用性测试仅告诉你关于特定解决方案的信息。

实验可能的结果及相应行动：

- 对齐的洞察 → 成为战略的一部分。
- 新的洞察 → 检查规模并判断是否需要调整。
- 无效的反馈 → 返回重新定义战略。
- 持续实验以发现更多关于问题和解决方案的信息。

## 第二部分：战略路线图

### 路线图简介

- 路线图可能是团队执行失败的核心原因，并导致团队像功能工厂一样运作。
- 路线图的不同定义：
    - 产品如何实现目标的可视化 → 展示产品的方向以及为实现目标所需的工作。
    - 定义目标或期望结果的战略计划，包括实现目标所需的主要步骤或里程碑。
    - 一种战略沟通工具，表达意图和方向的声明。
- 路线图的属性：
    - **战略计划** → 对问题和机会进行排序和安排，并为其分配高级时间框架。
    - **以结果为导向** → 关注结果，而非输出或可交付成果。
    - **沟通工具** → 路线图将产品战略与产品执行联系起来。
- 路线图的悖论/陷阱：
    - 将其视为约束性计划 → 精确构建我们6个月前认为可行的内容（没有学习且可能错误）。
    - 将其视为指南 → 改变方向却感觉像是欺骗了你。
- 有争议的事项：
    - 时间范围 → 当我们不知道需要多少精力时。
    - 解决方案或目标 → 过早地记录功能/解决方案可能会限制我们关注于次优问题或选择次优解决方案。
    - 细节级别 → 史诗或故事。
    - 随时间推移的不确定性 → 未来变得更加模糊。
    - 承诺 → 这是约束性协议吗？
- **将讨论重点转向结果。**
    - 谈论结果的障碍包括：信任、团队问责制、奖励制度（例如：庆祝交付）、接受不确定性（实验和失败）。
    - **以结果为导向是产品组织可以做出的最关键转变，而战略路线图可以成为关键工件。**
- 路线图讨论是战略与执行交汇的地方 → 在此阶段讨论结果而不是输出奠定了基调。
    - 产品负责人应将讨论重点放在我们想要解决的问题上。
- **项目计划隐藏了创造实现结果产品的不确定性。**
- **聚焦于战略路线图：**
    - 对战略驱动因素的深入细分。
    - 考虑创建成功路径的排序和里程碑。
    - 它应反映我们计划如何实现战略，以及我们何时期望实现关键的里程碑。
    - 将战略驱动因素分解为更小的问题以解决 → 确定分配给每个团队的数量。

---

路线图制定过程

- 从理解以下内容开始：
    1. **输入**
        - 产品战略（主要输入）。
            - 使用驱动因素 → 将其分解为更小的部分。
        - 当前路线图。
            - 这些内容仍然相关吗？
            - 记得与利益相关者沟通变更。
        - 当前团队结构和定义。
    2. **涉及的人员**
        - 在需要的细节和职责之间找到合适的平衡，同时避免过多参与者。
        - 谁应参与？
            - 产品领导层、技术领导层和职能经理（UX负责人、产品等）。
            - 根据平衡有益的输入与决策延迟，邀请其他利益相关者。
    3. **节奏**
        - 它们是战略的表达，因此条目可以持续12个月。
        - 我们需要为实验学习留出空间。
        - **持续更新你的路线图**。
        - 设置要解决的问题，但解决方案可以变化。
        - 如果问题发生变化，更新利益相关者。

---

自上而下 vs 自下而上

- **自主的产品团队应追求自下而上的目标**（他们更接近用户、指标和技术）。
- **但我们希望将组织对齐到一个方向** → 选择一条单一路径并自上而下传递。
    - **目标是最大化整个系统的输出，而不仅仅是局部团队。**
- 我们希望团队参与并承诺。
- **但我们也需要推动对齐。**
- 离产品执行越近，团队在决策中的影响就应该越大。
- 战略应自上而下。
- OKR应受到团队的高度影响。
- **战略路线图应位于中间。**

### 路线图结构

- **你需要选择正确的路线图结构**

![[Notion/42向量/领域圣经/成长-关系-职场/assets/《10x Is Easier Than 2x》10倍比2倍容易/image 193.png]]

- **反映未来的不确定性，但现在是清晰的**
- 所有路线图都有时间组件（即使是“现在”、“下一步”、“未来”）。
- 对近期项目使用更精确的定义：
    - 例如：将“提高用户留存率”细化为“通过增加通知和电子邮件点击率来提高前7天的留存率”。
- 对较短时间段使用更精确的时间线：
    - 例如：Q1、Q2、H2（或“明年”）。
- **关注机会和问题，而非解决方案**
- 使所有人聚焦于客户和业务问题。
- 留出探索的空间，允许解决方案变化和实验。
- **专注于将路线图元素写为挑战**。
- 不列出功能，专注于挑战或结果。
- **目标导向**
- 战略目标应始终存在（无论作为泳道还是其他视觉呈现）。
- 将与战略目标相关的内容分组。
- **反映所有主要工作，即使它们不是战略性的**
- 消耗大量时间和精力的任何事项都应包括进来。
- 将它们纳入路线图，因为路线图关乎对齐和沟通。
- **路线图不是约束性计划** → 每个人都需要对变化保持开放。
- 不要花费过多时间创建路线图 → 以免不愿更改它。
- 以迭代方式开发路线图 → 对新学习和变化保持开放。

---

轴的定义

- **不要忽视轴的强大作用** → 使用并定义它。
- 如果可以，与其他团队保持一致。
- 水平轴上坚持时间框架：
- 如果使用时间段...
    - 避免使用月（过于详细）。
    - 使用季度（Q1、Q2）、半年度（H2）、明年（NY）。
- 或使用...
    - 现在、下一步、未来。
    - 需要具体日期时，可能会使讨论变得更困难。

---

垂直轴或泳道

- 使用泳道进行分组：
- 你可以使用主题（例如：产品团队需要解决的客户需求）。
    - 可以将主题细分为子主题。
- 可以使用泳道表示不同的产品或团队（但这可能使你远离战略）。
- 可以按目标分组（例如：提高转化率15%）。
- **在战略路线图中 → 按战略目标排序：**
    - 用户目标，然后使用主题作为次级划分。
    - 或选择可以分组目标的主题。

---

网格中的项目/卡片

- **标题与卡片**
- 许多路线图是工具的截图，让你可以点击标题查看更多信息。
- 卡片允许你在标题之外添加更多信息，但空间有限，因此需要商定格式，同时保留灵活性。
- **粒度**
- 你需要决定并传达路线图的粒度级别：
    - **尽可能接近执行 → 但同时留有探索和实验最佳解决方案的空间。**
    - 示例：
        - 太一般：减少每次销售的客户服务呼叫比例20%。
        - 更好：通过改进在线搜索和答案提供减少信息呼叫请求。
- **规模的经验法则：**
    - 对于时间段，大小适中 → 允许未来的时间段更模糊。
    - 可执行（不用是解决方案） → 团队可以轻松采取行动。
    - 影响是可衡量的 → 考虑影响指标并具有量化结果。
- **措辞选择：**
- 使用动词（例如：改进优惠券信息）、准确的名词（优惠券信息）或目标导向的表达（例如：通过改进优惠券减少10%的信息呼叫）。
- **视觉化表示的内容：**
- 机会生命周期阶段（例如：问题发现、解决方案发现、交付）。
- 成本（例如：较大的项目需要更长时间完成且成本更高）。
- 类别或项目组（特别是在未作为轴时）。
- **表示方式：**
- 颜色。
- 标签。
- 尺寸。
- 图标。

战略梳理

- 将你的战略分解成路线图。
- 确定每个单元格中适合的项目。
- 将问题分解为机会，并降低定义层级：
    - 如果你已经完成了探索工作，可以更详细地定义。
    - 其他领域可能需要保持较高层次，因为它们基于假设并需要进一步研究。
- 抽象的机会在中长期内是可以接受的。
- **LRM（最后责任时刻）** → 一种敏捷原则，在需要之前推迟对项目进行分析或决策。

---

达到路线图项目的不同方法：

**机会树**

- 用它来识别多个洞察，并将它们映射到高级机会上。
- 选择并综合你的驱动因素 → 然后树中的较低节点可以成为主题和路线图项目。
    - 高级机会 → 主题。
    - 较低级别的选项 → 路线图元素。
- 仅包括你在战略定义中选择的项目。
- 机会树帮助你映射多个替代方案并选择最佳方案：
    - 通过输入分析或实验完成。


**客户旅程图**

- 描述用户在使用产品/服务以实现目标时所执行的一系列活动。
- 选择你想关注的目标 → 使用旅程地图识别可以改进的低级别旅程环节。
- 你正在将痛点和机会映射到旅程中的每项活动。
- 它可以提供实现战略目标的不同方法。
- 参阅《Mapping Experiences》第10章，了解如何制作旅程图。
- 客户旅程图会引发长时间详细的讨论 → 因此可能难以保持战略性。
    - **但它在创造机会方面非常出色。**
    - 你可能会深入研究旅程中的某一部分。


**传统切分**

- 在敏捷中，切分用于将用户故事分解得足够小以适应迭代，同时仍然增加价值 → 你也可以在路线图层级使用这种技术。
- 切分模式：
    - 用户段（用户组A，用户组B）。
    - 地理位置（区域A，区域B）。
    - 活动/操作（例如：购买、退货）。
    - 工作流程（例如：x在y之前）。
    - 变体：在你的场景中有哪些变化？哪种切分方向最合理？

---

包含其他必要工作

- 你应该始终考虑那些不被视为战略的一部分但却是强制性工作。

关于技术债务的处理方式：三种选择

9. **20%规则** → 持续投资，然后你就不需要在路线图中体现它。
10. **展示战略重构**（当技术债务推动或支持你的战略时）。
11. **非业务战略性必要重构** → 例如：从单体架构迁移到服务架构。

---

花时间将内容写好

- 在不失去意义的情况下保持名称简短 → 从一个想法中选择最强的词。
- 让不同受众都能轻松理解。
- 遵循相同的命名结构。

优先级和时间线

- 理想情况下，你需要确定每个项目的优先级，并将其按时间顺序安排。
    - 考虑工作量、资源、依赖关系和不确定性。
- **4种方法：**
    1. **传统的价值 vs 努力**
        - **不要使用它**
        - 我们对于估算价值和努力非常糟糕。
        - 使用探索中获得的证据，而不是猜测价值。
    2. **时间范围**
        - 未来时间范围的项目不需要严格的优先级。
        - 将它们包含在适当的时间框架中（时间框架应与结果实现的时间点匹配，而不是赌注开始的时间点）。
        - 如果有意义，可以将较长的工作分配到“现在/下一步/以后”。
    3. **根据战略结果确定优先级**
        - **使用这个方法**
        - 使用战略选择输入来为项目确定优先级。
        - 使用假设和预期结果来优先考虑更有意义的内容。
            - **如何设置时间框架？** → 猜测实现结果的时间点 → 允许迭代、实验和其他不可预测的项目。
    4. **不使用信心水平进行优先级排序**
        - 我们倾向于偏爱风险较低且更确定的事情。
        - **不要使用这种方法** → 而是直接通过探索面对不确定性。
        - 拥抱不确定性，优先考虑正确的机会，并快速通过实验验证假设或调整方向。

---

应用/电子表格和跨团队一致性

- 专用软件使一致性更容易：
    - 专用软件可以与Jira集成。
    - 专用软件可以基于过滤器或时间范围改变视图（使用PowerPoint或电子表格需要大量格式调整和活动迁移）。
    - 使用专用软件更容易编制投资组合路线图。
    - **但你会失去变化性，并且需要支付许可费用**。

---

是否考虑组织结构？

- 考虑它会让你为每个团队分配适量的工作量。
    - 但我们不擅长估算。你需要一个可行性的概念，但精确度并不可能。
- 不同资源/诊断和行动：
| 资源诊断 | 行动 |
| --- | --- |
| 在选定方向上加速推进 | 重新分配资源或降低其他机会的优先级 |
| 检测到过载和不足 | 根据新战略平衡资源 |
| 当前未被拥有的新工作领域 | 将所有权交给现有团队或创建新团队 |

---

**许多领导者因无所作为而未能通过重新分配资源加速选定方向**

- 一旦你确定了战略，请寻找加速的方法：
    - **考虑：**
        - 小团队调整。
        - 重新聚焦团队。
        - 重新分配团队（将部分产品转入维护模式）。
- **考虑重组** → 但这需要仔细考虑、沟通和执行。
    - **长期团队是产品文化的支柱。**
    - 一致性的变化将产生负面影响。

---

沟通与反馈

- 在整个组织中广泛分享你的路线图。
- **主要沟通目标：对齐和共享理解。**
- **路线图会话有三个重点领域：**
    1. **你想解决什么问题？**
        - 战略告诉你：你要去哪里以及需要哪些机会来实现目标。
        - 现在，你有了这条路径的可视化。
        - 路线图应让每个人都能看到需要解决的问题。
    2. **为什么你为这些机会选择了这个顺序？**
        - 解释你的优先级逻辑。
        - 分享你的分析和假设，以创建共享理解。
    3. **为什么你遵循这个时间框架？**
        - 分享为什么某些项目比其他项目需要更长时间。
        - 与解决方案未知的不确定性作斗争。
            - **承诺影响和关键结果...而不是功能交付日期。**
- **根据受众调整你的展示细节。**
    - 你应该只有一个路线图 → 但能够以不同深度的方式展示它。
- **在任何广泛会议之前达成高级别的一致意见：**
    - 一开始就共同创建路线图。
    - 然后，在更广泛的会议之前，协调最有影响力的利益相关者。
    - 提前讨论困难的话题 → 确保会议中没有负面惊喜。
    - 提出复杂问题和权衡，展示你的工作及其决策依据。
    - **调整你的提案以涵盖反馈，这将增加获得高管支持的可能性。**

---

处理利益相关者的反馈：

- 战略沟通比路线图沟通更容易。
- 对路线图的反馈会更加强烈。
- **你将错过一些期望...**
    - **为什么x不在路线图上？**
        - 回到数据。
        - 询问还有哪些东西应该被移除。
        - 同意测试（收集更多信息或进行一些实验）。
- **对变化保持开放** → 以开放的心态参加会议，并适应以最大化影响。

---

不确定性反馈：

- **你是否会构建功能x？**
    - 如果你已经进行过探索，你将充满信心。
    - 如果是新的机会，你可以承诺进行实验并收集与提议解决方案相关的洞察。
    - **包含“可能的解决方案字段”以明确你将测试或研究某种方法。**
- **时间不确定性：什么时候会构建x？**
    - 解释你尚不知道解决方案，或者实现指标需要迭代的时间。
    - 将利益相关者从计划心态转向战略心态。
    - 将重点放在问题的优先级和顺序上。
    - 为短期项目设定目标季度，以便你看到期望的结果。
    - 标记固定日期项目（错过日期就会失去机会）。

---

对齐

- 告诉其他团队你需要他们提供什么。
- 告诉其他团队他们可以如何帮助推动战略。
    - **考虑营销、运营、法律和财务。**
- **在路线图沟通之前安排战略沟通**，因为战略是路线图决策的基础，而你将没有空间适应。

---

沟通路线图变更：

- 路线图应该是动态的。
- 随着你的学习进行更新。
    - 随进度添加细节。
    - **战略变化 → 立即沟通。**
    - **未实现的目标** → 考虑延长时间，如果这些目标是最重要的事情...除非情况发生变化，否则继续推进可能仍然是最好的选择。
        - 如果目标尚未实现，按季度沟通。

## 第三部分：目标与关键结果（OKRs）

---

### OKRs简介

- 目标与关键结果（OKRs）是一种目标设定框架。
- 起源于英特尔，被谷歌和其他公司采用。
- OKRs 将愿景与相关指标结合在一起：
    - **我将（目标）通过（关键结果集）来衡量。**
- 看似简单，但需要几个季度的练习，团队才能完全掌握。
- **目标：** 一种激励人心的目标，它设定了明确的方向并帮助激励团队。
- **关键结果：** 既是一个指标也是一个目标值。它们帮助团队判断方向是否正确。
    - 关键结果是具体的、可测量的和可验证的。
- **时间限制：** OKRs 是一种有时间限制的目标系统，关键结果应在特定时间点完成（通常是季度或年度）。
- 每个目标可以有几个不同的关键结果。
- **基础步骤：** 设定 → 检查 → 最终评估。
- OKRs 支持你的产品方向，并帮助创建自主、独立且以结果为导向的产品团队。其特点包括：
    - **以结果为导向：** 专注于为用户带来的价值，而不是团队的活动。该格式支持团队自主性。
    - **具有挑战性：** 设定具有挑战性的目标。良好的得分是 70% 而非 100%。
        - **谷歌原则：设定我们目前无法达到的目标，因为我们知道，通过努力实现这些目标，我们能比预期更进一步。**
    - **透明性：** 每个人都能看到彼此的目标。
        - “OKRs 为任何部门的任何人提供了必要的上下文，以了解团队或个人试图实现的目标。”
    - **一致性：** 检查团队是否与公司目标保持一致。
        - 级联目标可能让人感觉像瀑布式流程。
        - OKRs 应是自下而上与自上而下的混合。
            - 公司目标设定方向，团队可以基于如何为每个期望结果作出贡献来创建目标。
    - **敏捷性：** 为变化留出空间，并按季度设定目标。
    - **聚焦：** 通过少量目标保持关注。
        - **关注更少的团队可以对重要事项产生更大的影响。**
        - 将目标数量保持在尽可能少（1个最佳，不超过3个）。
        - 如果你有3个目标和3个关键结果，你每个关键结果只有1周时间。

| 目标数 | 每个目标的关键结果数 | 总关键结果数 | 每个关键结果的周数 |
| --- | --- | --- | --- |
| 3 | 3 | 9 | 1.3 |
| 4 | 4 | 16 | 0.75 |
| 4 | 5 | 20 | 0.6 |
- 在某些情况下，很难完全以结果为导向。务实并允许例外，但不要陷入以下陷阱：
    - 法律或合规要求。
    - 重构或内部能力。
    - 内部代理与实际结果。
    - 部分工作。

---

### 管理 OKRs 的流程

- **阶段：** 创建 + 检查 → 最终评估。
- **创建阶段：** 在几周内完成四个步骤：
    1. 区域和团队草案。
    2. 依赖关系和反馈循环。
    3. 最终值和质量审查。
- **OKRs 的输入：** 战略路线图 + 当前团队结构。
- **涉及的人员：**
    - 让团队拥有目标的制定权。
    - 高级经理可以帮助进行对齐和衡量质量 → 但不决定团队使用什么指标或目标值。
        - **如果你觉得需要控制目标 → 你需要为团队提供更多战略背景。**
    - 你的战略和沟通不清晰。
    - 产品经理应拥有 OKRs。
    - 技术负责人和设计负责人应是定义过程中的关键决策者。
    - 职能经理可以审查对齐情况，并协调依赖关系和结果定义质量。
    - 相关利益相关者（尤其是他们有相关关键结果时）。
- **你需要产品区域 OKRs 吗？**
    - 它们可能会造成混乱和重复。
    - 但它们也有一些好处：
        - 帮助衡量跨产品结果。
        - 团队可以看到他们的贡献。
        - 帮助产品领导层简化与管理层的对话。
        - 产品区域 OKRs 可以为团队提供明确的战略方向。
- **节奏：使用季度**
    - 将检查频率与团队能够影响结果的速度相匹配（从1周到6周）。
- **流程图：**
    - 区域草案 → 团队草案 → 依赖关系管理 → 最终版本 → 定期检查。

| 周数 | 活动 |
| --- | --- |
| 第0周 | 准备就绪 |
| 第-1周 | 最终目标与审查 |
| 第-2周 | 依赖关系和冲突解决 |
| 第3周 | 区域草案/团队草案 |

### 定义区域和团队的 OKRs 草案

- **创建目标的初稿**
    - **使用你的战略驱动因素或路线图主题作为目标**
        - 你的机会解决树可以提供帮助。
    - **关键结果的定义通常比路线图项目更详细**
        - 一个单一的路线图项目可能包含多个关键结果。
    - **你可以将关键结果分组到与你团队结构对齐的目标中**
        - 将 OKRs 与团队对齐比与路线图项目对齐更重要。

---

### 选择更具体指标的工具

- **指标框架：**
    - AARRR → 适用于 SaaS 产品。
    - 转化漏斗 → 电子商务。
    - 谷歌的 HEART → 适用于大多数产品，专注于用户体验。
    - 客户参与的 3 个层次 → 根据“注意力、购买或生产力”来识别更重要的指标。
- **KPI 树帮助可视化并探索哪些子指标会影响你期望的结果**
    - **确保你使用的关键结果与要解决的问题最具体相关**。
    - KPI 树可以通过两种方式找到指标：
        - 从顶部开始，将 KPI 分解为组成部分。
        - 或检测影响低级别指标的机会，从而推动更高级别的结果。
- **领先指标：**
    - 找到今天受影响的指标，这些指标能影响期望的结果。
        - 例如：客户生命周期价值是一个滞后指标。
        - 例如：提高任务完成率是一个领先指标。
    - 它们更容易从一次迭代到下一次迭代中测量，创建更快的反馈循环，团队能更快地判断是否影响了其关键结果。
    - **选择一个领先指标是假设它将改变期望结果。**
- **分段：**
    - 分段可以帮助创建更好的关键结果。
    - 分段方式多种多样：
        - 人口统计、心理特征、行为特征、公司特征（适用于 B2B）。
- **OKR 链接是一个强大的对齐工具：**
    - 声明你的 OKR 所贡献的更高级别目标。
    - 你可以链接到产品部门 OKRs 或业务单元目标。
    - 链接和对齐的挑战：
        - 间接关系 → 可能无法直接归因。
        - 缺乏相关的公司目标 → 例如：维护 OKRs。若无相关目标，说明缺乏战略对齐。
        - 链接到多个业务单元 → 可能会链接到共享服务领域。

---

### 依赖关系和反馈

- **跨团队修订检查目标是否在整个组织中具有逻辑性和一致性**
    - 检查依赖关系、审查高期望值并调整草案。
    - 如果涉及的团队数量多或底层技术架构与你对立，可能需要一周时间来解决。
- **某些 OKRs 会向其他团队发出请求，因为它们依赖于其他团队来实现其结果**
    - **这是横向动态（不仅仅是自上而下或自下而上）**
    - **打破孤岛，促使同级协作，共同定义最佳实现战略目标的方式。**
- **如果选择帮助所有依赖团队，有些团队可能会有太多目标**
    - **他们可以请求放弃或延迟某些请求。**
- **目标依赖关系推动团队讨论组织最关键的结果**
    - 要求团队与所有依赖团队会面 → 共同做出决定：
        - **如果你提供了足够的战略背景，这可以赋能团队解决问题。**
- **通过设计降低依赖关系**
    - 建造任何东西都需要大量团队的努力。我们有两个选择：
        1. 增加协调和控制，决定要进行哪些计划。
        2. 投资于让团队更加独立。
    - **尝试管理复杂依赖关系（例如 Scaled Agile Framework Enterprise (SAFe)）往往会阻碍创建自主和赋权团队的意图。**
    - **成功的产品组织通常选择减少协调需求，投资于支持团队自主性的架构和实践。**
    1. 工具：模块化架构、DevOps、内部开源。
    2. 衡量你的投资组合活动中有多少依赖关系。

---

### 最终值与季度评估

- **让团队自我评估其 OKRs 的质量**
| 属性 | 描述 |
| --- | --- |
| **以结果为导向** | 将其表述为预期结果而非任务。 |
| **独立或共享** | 要么通过具体化隔离你的结果，让团队可以控制它；要么与其他团队合作完成相同的关键结果。 |
| **粒度** | 明确你试图推动的领先指标。 |
| **明确的测量标准** | 精确说明你的关键结果如何被验证，例如“销售额增加10%”...相对于哪个基准？ |
| **适当时间跨度** | 对于较小的努力，设定更积极的时间表；对于较大的任务，找到早期能提供价值的小里程碑。 |
| **平衡关键结果** | 使用平衡的关键结果，避免以任何成本追求目标，并识别需要保护的相关指标。 |
| **挑战水平** | 选择一个关键指标作为关键结果（不要包括所有）。以历史表现为基准，校准挑战水平。 |
- 各领域负责人应提供第二次评审，帮助团队提高 OKR 质量。

---

### OKR 检查、更新和沟通

- **建立定期的检查点并促进对情况的分析**
    - **每个团队根据定义的关键结果更新其目标、值和状态**
- 包括任何洞察或预测，说明你预计值将如何变化。
- **跨团队审查 → 快速同步所有产品团队的整体结果**
    - 每个人都应朝着相同战略努力 → 每个人都应关心其他团队的成功、失败和学习。
    - 包括：状态（表现良好与否）、结果亮点（关键结果指标变化）、学习（关于假设）。
- **官方更新可作为触发器，改变计划并提高对偏离目标的意识**
- **OKR 审查结果可能导致：**
    - 无新行动（目标在轨）。
    - 正常计划修改（改变计划和策略，但目标保持不变）。
    - 消除、改变或添加目标（根据当前结果或特殊情况）。
- **绝不应有改变 OKRs 的正式流程**，团队应被授权直接更改它们，并保持对齐（特别是依赖团队）。

---

### 最终检查如何影响下一季度

- 基线可能会为未来的关键结果而变化。
- 未来工作可能需要实现之前的目标。
- 过去的结果可能会使我们当前的定义无效。

### 结论

- **产品方向选择我们想要专注于发现和交付的问题和目标。**
- **简单模型：**
    - **方向**：选择正确的领域。
    - **发现**：验证正确的解决方案。
    - **交付**：实现正确的结果。
- 作者认为，产品方向优先于设计双钻模型。
| 钻石阶段 | 分散 | 汇聚 | 结束于 |
| --- | --- | --- | --- |
| **方向** | 洞察 | 战略选择 | 问题与目标 |
| **定义问题** | 发现 | 定义 | 定义与假设 |
| **定义解决方案** | 构思 | 验证 | 验证后的解决方案 |
